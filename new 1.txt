# ТЗ: уведомления о релизных слотах из YouTrack в Pulse

## 1. Цель

Реализовать автоматическую отправку уведомлений в канал Pulse по релизным слотам из YouTrack.

DAG должен:

* ежедневно парсить карточки YouTrack с типом `Release Slot`;
* сохранять актуальную информацию по карточкам в существующие таблицы;
* ежедневно проверять изменение поля `Фактическая дата релиза`;
* при изменении даты релиза отправлять уведомление о переносе в Pulse;
* по понедельникам дополнительно отправлять расписание релизов на текущую неделю.

## 2. Название DAG

`yt_release_schedule`

## 3. Расписание запуска

DAG запускается каждый день в 09:00.

Логика запуска:

* каждый день выполняется синхронизация карточек из YouTrack;
* каждый день проверяются изменения фактической даты релиза;
* если день запуска — понедельник, дополнительно отправляется расписание релизов на текущую неделю.

## 4. Источник данных

Источник данных — YouTrack.

Необходимо получать задачи с типом карточки:

`Release Slot`

Фильтр по дате:

* брать релизные слоты от текущего дня;
* горизонт проверки — 7 дней вперед;
* дата определяется по custom field `Фактическая дата релиза`.

## 5. Целевые таблицы

Данные необходимо записывать в существующие таблицы:

```sql
tech_etl.yt_issue_worklog
tech_etl.yt_issue_timeline
tech_etl.yt_issue_snapshot
tech_etl.yt_issue_custom_field
tech_etl.yt_issue_comment
```

Логика загрузки уже частично реализована в релизном DAG, ее необходимо переиспользовать.

Важно:

* таблицы не транкейтить полностью;
* в таблицах хранится актуальное состояние карточек, не SCD;
* по одной карточке в `tech_etl.yt_issue_snapshot` должна быть одна актуальная запись;
* по одному полю карточки в `tech_etl.yt_issue_custom_field` должна быть одна актуальная запись на комбинацию `issue_id + field_name`;
* если карточка уже есть, необходимо обновлять ее актуальное состояние;
* если карточки еще нет, необходимо вставить новую запись;
* если изменилось поле `Фактическая дата релиза`, необходимо отправить уведомление о переносе;
* если поле `Фактическая дата релиза` не изменилось, уведомление не отправлять.

## 6. Основные поля для сообщения

Для формирования сообщений использовать данные из `tech_etl.yt_issue_snapshot`:

* `issue_id`;
* `summary`;
* `assignee`;
* `current_state`;
* `updated_at`;
* `dttm_loaded`.

Из `tech_etl.yt_issue_custom_field`:

* `Тип карточки`;
* `Assignee`;
* `Направление`;
* `Номер релиза КХД`;
* `Фактическая дата релиза`;
* `State`.

## 7. Логика синхронизации данных

DAG должен:

1. Получить из YouTrack карточки типа `Release Slot`.
2. Получить по ним snapshot, custom fields, comments, timeline, worklog.
3. Сравнить полученные значения с текущими данными в таблицах.
4. Для новых карточек выполнить insert.
5. Для существующих карточек выполнить update актуальных значений.
6. Перед update проверить, изменилось ли поле `Фактическая дата релиза`.

Рекомендуемая логика:

* сначала прочитать старое значение `Фактическая дата релиза` из `tech_etl.yt_issue_custom_field`;
* затем получить новое значение из YouTrack;
* если старое значение отличается от нового — зафиксировать событие переноса и отправить уведомление;
* после этого обновить значение в таблице.

## 8. Проверка изменения даты релиза

Основной критерий отправки уведомления о переносе:

```text
значение custom field "Фактическая дата релиза" изменилось относительно текущего значения в БД
```

Сравнение выполнять по `issue_id`.

Пример логики:

```sql
select
    old_f.issue_id,
    old_f.field_value as old_release_date,
    new_f.field_value as new_release_date
from old_fields old_f
join new_fields new_f
    on old_f.issue_id = new_f.issue_id
   and old_f.field_name = new_f.field_name
where old_f.field_name = 'Фактическая дата релиза'
  and coalesce(old_f.field_value, '') <> coalesce(new_f.field_value, '');
```

Если значение изменилось:

* сформировать сообщение о переносе;
* отправить сообщение в Pulse;
* обновить поле в `tech_etl.yt_issue_custom_field`.

Если значение не изменилось:

* сообщение не отправлять;
* данные обновляются в штатном режиме, если изменились другие поля.

## 9. Логирование отправленных уведомлений

Чтобы не отправлять одно и то же уведомление повторно, создать служебную таблицу:

```sql
create table if not exists tech_etl.yt_release_notifications_log (
    issue_id text not null,
    notification_type text not null,
    old_release_dttm timestamp null,
    new_release_dttm timestamp null,
    pulse_message text null,
    sent_flg boolean default false,
    sent_dttm timestamp null,
    dttm_created timestamp default now()
)
distributed by (issue_id);
```

Для уведомления о переносе использовать:

```text
notification_type = 'RELEASE_DATE_CHANGED'
```

Перед отправкой уведомления проверять, что такое событие еще не было успешно отправлено.

## 10. Формат уведомления о переносе релиза

Если дата релиза изменилась, отправлять сообщение:

```text
🔄 Перенос релиза

Релиз: FI
Карточка: DWH-10315
Ответственный: Zernov Aleksandr

Было: 26.06.2026 18:00
Стало: 28.06.2026 18:00

Ссылка на карточку: <ссылка>
```

Правила заполнения:

* `Релиз` брать из `summary` или из поля `Направление`, если так удобнее;
* `Карточка` — `issue_id`;
* `Ответственный` — custom field `Assignee`, если заполнен, иначе `yt_issue_snapshot.assignee`;
* `Было` — старое значение поля `Фактическая дата релиза`;
* `Стало` — новое значение поля `Фактическая дата релиза`;
* `Ссылка на карточку` формировать по шаблону YouTrack URL.

## 11. Формирование расписания релизов на неделю

Если день запуска DAG — понедельник, необходимо отправить расписание релизов на текущую неделю.

Расписание формируется из актуальных данных в БД, а не напрямую из YouTrack.

Период:

```sql
date_trunc('week', current_date)::date
```

по

```sql
date_trunc('week', current_date)::date + interval '7 day'
```

То есть понедельник–воскресенье текущей недели.

## 12. SQL для получения сообщения расписания

```sql
with release_slots as (
    select
        s.issue_id,
        s.summary,
        s.current_state,
        s.assignee as snapshot_assignee,

        max(case when f.field_name = 'Тип карточки' then f.field_value end) as issue_type,
        max(case when f.field_name = 'Assignee' then f.field_value end) as assignee,
        max(case when f.field_name = 'Направление' then f.field_value end) as direction,
        max(case when f.field_name = 'Номер релиза КХД' then f.field_value end) as release_number,
        max(case when f.field_name = 'Фактическая дата релиза' then f.field_value end) as release_date_txt,
        max(case when f.field_name = 'State' then f.field_value end) as state
    from tech_etl.yt_issue_snapshot s
    join tech_etl.yt_issue_custom_field f
        on s.issue_id = f.issue_id
    group by
        s.issue_id,
        s.summary,
        s.current_state,
        s.assignee
),

final as (
    select
        issue_id,
        summary,
        coalesce(direction, 'Не указано') as direction,
        coalesce(assignee, snapshot_assignee, 'Не назначен') as assignee,
        release_number,
        coalesce(state, current_state) as state,
        nullif(release_date_txt, '')::timestamp as release_dttm
    from release_slots
    where issue_type = 'Release Slot'
      and nullif(release_date_txt, '') is not null
)

select
    '🚀 Релизное расписание на неделю' || chr(10) ||
    'Период: ' ||
    to_char(date_trunc('week', current_date)::date, 'DD.MM.YYYY') ||
    ' — ' ||
    to_char((date_trunc('week', current_date)::date + interval '6 day')::date, 'DD.MM.YYYY') ||
    chr(10) || chr(10) ||

    coalesce(
        string_agg(
            '📅 ' || to_char(release_dttm, 'DD.MM.YYYY HH24:MI') || chr(10) ||
            '• ' || summary || chr(10) ||
            'Направление: ' || direction || chr(10) ||
            'Ответственный: ' || assignee || chr(10) ||
            'Номер релиза: ' || coalesce(release_number, '-') || chr(10) ||
            'Статус: ' || coalesce(state, '-') || chr(10) ||
            'Карточка: ' || issue_id,
            chr(10) || chr(10)
            order by release_dttm, direction, summary
        ),
        'На текущую неделю релизные слоты не найдены.'
    ) as pulse_message
from final
where release_dttm::date >= date_trunc('week', current_date)::date
  and release_dttm::date <  date_trunc('week', current_date)::date + interval '7 day';
```

## 13. Интеграция с Pulse

Сообщения отправлять в заранее созданный канал Pulse.

Параметры необходимо вынести в Airflow Variables или Connections:

* `pulse_api_url`;
* `pulse_token`;
* `pulse_release_channel_id`.

Сообщение считается отправленным только после успешного ответа Pulse API.

## 14. Конфигурация Airflow

Вынести в Airflow Variables или Connections:

* `youtrack_url`;
* `youtrack_token`;
* `youtrack_release_slot_query`;
* `pulse_api_url`;
* `pulse_token`;
* `pulse_release_channel_id`;
* `youtrack_issue_url_template`.

Пример шаблона ссылки:

```text
https://youtrack.company.ru/issue/{issue_id}
```

## 15. Обработка ошибок

Если YouTrack API недоступен:

* DAG должен завершиться с ошибкой;
* ошибка должна быть видна в логах Airflow;
* данные в таблицах не должны обновляться частично.

Если Pulse API недоступен:

* сообщение не считается отправленным;
* ошибка должна быть видна в логах Airflow;
* событие уведомления должно остаться неотправленным в `tech_etl.yt_release_notifications_log`;
* при следующем запуске DAG необходимо повторить отправку.

Если у карточки некорректно заполнена `Фактическая дата релиза`:

* карточку не учитывать в расписании;
* записать предупреждение в лог;
* DAG не должен падать из-за одной некорректной карточки.

## 16. Контроль качества данных

Перед запуском в промышленную эксплуатацию проверить, что нет дублей:

```sql
select issue_id, count(*)
from tech_etl.yt_issue_snapshot
group by issue_id
having count(*) > 1;
```

```sql
select issue_id, field_name, count(*)
from tech_etl.yt_issue_custom_field
group by issue_id, field_name
having count(*) > 1;
```

Оба запроса должны возвращать 0 строк.

## 17. Критерии приемки

Задача считается выполненной, если:

1. DAG `yt_release_schedule` запускается каждый день в 09:00.
2. DAG получает из YouTrack карточки типа `Release Slot`.
3. Данные сохраняются в таблицы `tech_etl.yt_issue_*` без полного truncate.
4. В таблицах хранится актуальное состояние карточек.
5. При изменении поля `Фактическая дата релиза` отправляется уведомление о переносе.
6. Повторные уведомления по одному и тому же изменению не отправляются.
7. По понедельникам отправляется расписание релизов на текущую неделю.
8. Расписание формируется из данных, сохраненных в БД.
9. В сообщениях отображаются: релиз, дата, направление, ответственный, статус, номер релиза и ссылка на карточку.
10. Ошибки YouTrack и Pulse логируются в Airflow.
