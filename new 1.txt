Почему раньше работало, а сейчас нет

Скорее всего одно из этого:

1. Вырос объем dm_calc.sd_sales_main_scm.
2. Вырос объем dds.sales_bundle_and_delivery_relationship.
3. Появились дубли/размножение по delivery_code.
4. Появился перекос по sales_bundle_code или delivery_code.
5. Устарела статистика.
6. Изменился план запроса.
7. На сегменте стало меньше доступного лимита workfile.
8. Поменялись данные так, что row_number стал сортировать намного больше строк.

Самое важное: ошибка на seg1 говорит, что проблема может быть не только в общем объеме, но и в перекосе данных. Один сегмент получил слишком много строк.

Что прям плохо в текущем блоке lake
1. Ты создаешь lake по всей истории

Сейчас lake собирается без ограничения по периоду и без ограничения по нужным sales_bundle_code.

from dm_calc.sd_sales_main_scm ssms
join dds.sales_bundle_and_delivery_relationship sd4798
    on ssms.delivery_number_sales = sd4798.delivery_code

А потом ниже, в base, ты все равно используешь только те sales_bundle_code, которые есть в:

dm_calc.sales_bundle_transport_hub_turnover_sdt0004

и попадают в период:

t4.dt_transportation_stage_start_p <= v_key_max
and coalesce(t4.dt_transportation_stage_start_r, current_date) >= v_key_min

То есть lake можно сильно уменьшить заранее.

2. Join может быть many-to-many

Если в sd_sales_main_scm по одной продажной поставке несколько строк, и в sales_bundle_and_delivery_relationship по этой же поставке тоже несколько строк, получится размножение.

Например:

ssms по delivery_number_sales = 5 строк
sd4798 по delivery_code = 20 строк

после join = 100 строк

Потом все это сортируется для row_number().

3. Нет фильтра по удаленным строкам в sd4798

В других местах скрипта ты часто пишешь:

is_deleted_code is null

А здесь нет:

join dds.sales_bundle_and_delivery_relationship as sd4798
    on ssms.delivery_number_sales = sd4798.delivery_code

Если в sd4798 есть исторические/удаленные строки, они тоже участвуют в join и увеличивают объем.

Если бизнес-логика позволяет, надо добавить:

and sd4798.is_deleted_code is null
Быстрый правильный фикс

Нужно перед lake создать маленький список нужных sales_bundle_code из t4, и только по ним строить lake.

Добавь перед созданием pg_temp.lake
drop table if exists pg_temp.t4_scope;

create temporary table pg_temp.t4_scope
with (
    appendonly = true,
    orientation = column,
    compresstype = zstd,
    compresslevel = 3
) as
select distinct
    t4.sales_bundle_code
from dm_calc.sales_bundle_transport_hub_turnover_sdt0004 t4
where t4.dt_transportation_stage_start_p <= v_key_max
  and coalesce(t4.dt_transportation_stage_start_r, current_date) >= v_key_min
  and t4.dt_transportation_stage_start_p <> coalesce(t4.dt_transportation_stage_start_r, '22991231'::date)
  and t4.transport_route_destination_hub_code like 'G%'
  and t4.sales_bundle_code is not null
distributed by (sales_bundle_code);

Почему это лучше

Было:

вся dm_calc.sd_sales_main_scm
× вся dds.sales_bundle_and_delivery_relationship
→ row_number по огромному набору

Стало:

сначала берем только нужные sales_bundle_code из t4 за расчетный период
→ по ним берем sd4798
→ по ним берем ssms
→ row_number по сильно меньшему набору

Это должно заметно снизить workfile.

Если нельзя добавлять is_deleted_code is null

Если бизнес говорит, что в lake должны участвовать и удаленные строки, убери это условие:

and sd4798.is_deleted_code is null

Но я бы сначала проверил, сколько оно отрезает:

select
    count(*) as total_rows,
    count(*) filter (where is_deleted_code is null) as active_rows,
    count(*) filter (where is_deleted_code is not null) as deleted_rows
from dds.sales_bundle_and_delivery_relationship;

Если удаленных много, это как раз могло раздуть join.

Что проверить перед запуском
1. Сколько строк дает старый join
select
    count(*) as join_rows,
    count(distinct sd4798.sales_bundle_code) as sales_bundle_cnt
from dm_calc.sd_sales_main_scm ssms
join dds.sales_bundle_and_delivery_relationship sd4798
    on ssms.delivery_number_sales = sd4798.delivery_code;
2. Сколько строк дает новый ограниченный join
select
    count(*) as join_rows,
    count(distinct sd4798.sales_bundle_code) as sales_bundle_cnt
from pg_temp.t4_scope scope
join dds.sales_bundle_and_delivery_relationship sd4798
    on sd4798.sales_bundle_code = scope.sales_bundle_code
   and sd4798.is_deleted_code is null
join dm_calc.sd_sales_main_scm ssms
    on ssms.delivery_number_sales = sd4798.delivery_code;

Если разница в разы — проблема найдена.

Проверка перекоса

Посмотри, нет ли sales_bundle_code, который дает очень много строк:

select
    sd4798.sales_bundle_code,
    count(*) as cnt
from pg_temp.t4_scope scope
join dds.sales_bundle_and_delivery_relationship sd4798
    on sd4798.sales_bundle_code = scope.sales_bundle_code
join dm_calc.sd_sales_main_scm ssms
    on ssms.delivery_number_sales = sd4798.delivery_code
group by sd4798.sales_bundle_code

limit 50;

Если сверху есть значения с десятками/сотнями тысяч строк — именно они могут валить row_number().

Еще важная проверка: не поменяется ли результат
