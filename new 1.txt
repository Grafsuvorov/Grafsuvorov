ок, если:

дубликатов ключей нет,

DDL у таблиц совпадает (типы/scale одинаковые),

то причина почти всегда в алгоритмике исполнения (окна/округление/NULL/соединения), а не в структуре. Ниже — «детектор расхождений», который без знания внутренней формулы покажет, в чём именно расходится поведение v1 и v2.

Скрипт запускай блоками сверху вниз — он pinpoint’ит отличие.

0) Базовые дельты и поля-виновники
WITH deltas AS (
  SELECT v1.calculation_code, v1.dt_valid_from,
         (v1.standard_price_amount - v2.standard_price_amount) AS d_stprs,
         (v1.moving_average_price_amount - v2.moving_average_price_amount) AS d_pvprs,
         (v1.average_weighted_stock_price_rule3_amount - v2.average_weighted_stock_price_rule3_amount) AS d_rule3,
         (v1.average_weighted_stock_price_rule2_prev_date_amount - v2.average_weighted_stock_price_rule2_prev_date_amount) AS d_rule2_prev,
         (v1.average_weighted_stock_price_rule2_next_date_amount - v2.average_weighted_stock_price_rule2_next_date_amount) AS d_rule2_next,
         NULLIF(v1.price_unit_code,'')  AS v1_peinh,
         NULLIF(v2.price_unit_code,'')  AS v2_peinh,
         NULLIF(v1.price_valuation_type_code,'') AS v1_vprsv,
         NULLIF(v2.price_valuation_type_code,'') AS v2_vprsv,
         NULLIF(v1.price_rule_code,'')  AS v1_rule,
         NULLIF(v2.price_rule_code,'')  AS v2_rule
  FROM userdata.material_price_calculation v1
  JOIN userdata.material_price_calculation_v2 v2 USING (calculation_code, dt_valid_from)
)
SELECT col, max_abs, n_rows
FROM (
  SELECT 'stprs' col, MAX(ABS(d_stprs)) max_abs, COUNT(*) FILTER (WHERE d_stprs IS DISTINCT FROM 0) n_rows FROM deltas
  UNION ALL SELECT 'pvprs', MAX(ABS(d_pvprs)), COUNT(*) FILTER (WHERE d_pvprs IS DISTINCT FROM 0) FROM deltas
  UNION ALL SELECT 'rule3', MAX(ABS(d_rule3)), COUNT(*) FILTER (WHERE d_rule3 IS DISTINCT FROM 0) FROM deltas
  UNION ALL SELECT 'rule2_prev', MAX(ABS(d_rule2_prev)), COUNT(*) FILTER (WHERE d_rule2_prev IS DISTINCT FROM 0) FROM deltas
  UNION ALL SELECT 'rule2_next', MAX(ABS(d_rule2_next)), COUNT(*) FILTER (WHERE d_rule2_next IS DISTINCT FROM 0) FROM deltas
  UNION ALL SELECT 'peinh(code)' , NULL, COUNT(*) FILTER (WHERE v1_peinh IS DISTINCT FROM v2_peinh)
  UNION ALL SELECT 'vprsv(code)',   NULL, COUNT(*) FILTER (WHERE v1_vprsv IS DISTINCT FROM v2_vprsv)
  UNION ALL SELECT 'rule(code)',    NULL, COUNT(*) FILTER (WHERE v1_rule  IS DISTINCT FROM v2_rule )
) s
ORDER BY n_rows DESC NULLS LAST, col;


Если numeric-дельты крошечные (10⁻⁹…10⁻⁶) — различается порядок округления. Если «кодовые» поля расходятся — это может менять формулы для конкретных строк.

1) Проверь, не влияет ли price_unit_code / «валюта/единица»

Расхождения часто проявляются только при peinh ≠ 1.

WITH j AS (
  SELECT v1.*, v2.*,
         (v1.standard_price_amount - v2.standard_price_amount) AS d_stprs
  FROM userdata.material_price_calculation v1
  JOIN userdata.material_price_calculation_v2 v2 USING (calculation_code, dt_valid_from)
)
SELECT
  COALESCE(NULLIF(v1.price_unit_code,''),'(NULL)') AS peinh_v1,
  COALESCE(NULLIF(v2.price_unit_code,''),'(NULL)') AS peinh_v2,
  COUNT(*) AS n_rows,
  SUM((d_stprs IS DISTINCT FROM 0)::int) AS n_diff
FROM j
GROUP BY 1,2
ORDER BY n_diff DESC, n_rows DESC
LIMIT 20;


Если «почти все» дельты приходятся на peinh != '1' (или на строки, где peinh в v1≠v2), значит в одном из пайпов применён пересчёт/деление/умножение в другом месте.

2) Проверь «пред/след дату» — окно стабильно ли одинаково?

Даже при одинаковых типах таблиц, алгоритм мог отличаться фреймом окна. Мы проверяем, что «предыдущее»/«следующее» в обеих таблицах трактуется одинаково (по позиции, а не по датному интервалу).

WITH base AS (
  SELECT 'v1' src, calculation_code, dt_valid_from,
         average_weighted_stock_price_rule2_prev_date_amount AS r2_prev,
         average_weighted_stock_price_rule2_next_date_amount AS r2_next
  FROM userdata.material_price_calculation
  UNION ALL
  SELECT 'v2', calculation_code, dt_valid_from,
         average_weighted_stock_price_rule2_prev_date_amount,
         average_weighted_stock_price_rule2_next_date_amount
  FROM userdata.material_price_calculation_v2
),
chk AS (
  SELECT src, calculation_code, dt_valid_from, r2_prev, r2_next,
         LAG(r2_next) OVER (PARTITION BY src, calculation_code ORDER BY dt_valid_from) AS prev_of_next,
         LEAD(r2_prev) OVER (PARTITION BY src, calculation_code ORDER BY dt_valid_from) AS next_of_prev
  FROM base
)
SELECT src,
       COUNT(*) FILTER (WHERE r2_prev IS DISTINCT FROM prev_of_next) AS bad_prev,
       COUNT(*) FILTER (WHERE r2_next IS DISTINCT FROM next_of_prev) AS bad_next
FROM chk
GROUP BY src;


bad_prev/bad_next должны быть 0 или близко к 0. Если нули в одной версии и >0 в другой — окно/порядок «шага по времени» реализованы по-разному.

Дополнительно убедись, что порядок в партиции одинаковый:

WITH ord AS (
  SELECT 'v1' src, calculation_code, dt_valid_from,
         ROW_NUMBER() OVER (PARTITION BY calculation_code ORDER BY dt_valid_from, calculation_code) AS rn
  FROM userdata.material_price_calculation
  UNION ALL
  SELECT 'v2', calculation_code, dt_valid_from,
         ROW_NUMBER() OVER (PARTITION BY calculation_code ORDER BY dt_valid_from, calculation_code) AS rn
  FROM userdata.material_price_calculation_v2
)
SELECT COUNT(*) AS rows_mismatch_order
FROM (
  SELECT v1.calculation_code, v1.dt_valid_from, v1.rn AS rn1, v2.rn AS rn2
  FROM ord v1
  JOIN ord v2 USING (calculation_code, dt_valid_from)
  WHERE v1.src='v1' AND v2.src='v2' AND v1.rn <> v2.rn
) t;


Если rows_mismatch_order > 0 — где-то иное сорт-условие (например, доп. tiebreaker), что меняет LAG/LEAD.

3) Проверь влияние NULL-ов/округления (одинаковая ли стадия округления)

Поменяй толеранс: 1e-12 → 1e-6 → 1e-2 и посмотри, где «исчезнут» дельты.

WITH p AS (SELECT 1e-12::numeric tol),
j AS (
  SELECT v1.calculation_code, v1.dt_valid_from,
         ABS(COALESCE(v1.standard_price_amount,0) - COALESCE(v2.standard_price_amount,0)) AS d
  FROM userdata.material_price_calculation v1
  JOIN userdata.material_price_calculation_v2 v2 USING (calculation_code, dt_valid_from)
)
SELECT
  COUNT(*) FILTER (WHERE d > 1e-12) AS n_d12,
  COUNT(*) FILTER (WHERE d > 1e-9 ) AS n_d9,
  COUNT(*) FILTER (WHERE d > 1e-6 ) AS n_d6,
  COUNT(*) FILTER (WHERE d > 1e-3 ) AS n_d3
FROM j;


Если дельты «падают» при ослаблении порога — 100% вопрос в месте округления (в v2 округляете раньше/позже).

4) Разложи дельты по «сценариям» — что лучше объясняет
WITH d AS (
  SELECT v1.calculation_code, v1.dt_valid_from,
         v1.standard_price_amount AS a1, v2.standard_price_amount AS a2,
         v1.price_unit_code       AS peinh1, v2.price_unit_code       AS peinh2,
         v1.price_valuation_type_code AS vprsv1, v2.price_valuation_type_code AS vprsv2,
         v1.price_rule_code AS rule1, v2.price_rule_code AS rule2
  FROM userdata.material_price_calculation v1
  JOIN userdata.material_price_calculation_v2 v2 USING (calculation_code, dt_valid_from)
),
x AS (
  SELECT *,
         (a1 IS NULL) AS s_null1, (a2 IS NULL) AS s_null2,
         (peinh1 IS DISTINCT FROM peinh2) AS diff_peinh,
         (vprsv1 IS DISTINCT FROM vprsv2) AS diff_vprsv,
         (rule1  IS DISTINCT FROM rule2 ) AS diff_rule,
         ABS(COALESCE(a1,0) - COALESCE(a2,0)) AS delta
  FROM d
)
SELECT scenario, COUNT(*) AS n_rows, SUM((delta>1e-9)::int) AS n_diff
FROM (
  SELECT CASE
           WHEN diff_peinh THEN 'A) разные price_unit_code'
           WHEN diff_vprsv THEN 'B) разные valuation_type'
           WHEN diff_rule  THEN 'C) разные rule_code'
           WHEN s_null1 OR s_null2 THEN 'D) NULL против значения'
           ELSE 'E) одинаковые входы, разный результат'
         END AS scenario,
         delta
  FROM x
) t
GROUP BY scenario
ORDER BY n_diff DESC, n_rows DESC;


Если всё попадает в «E) одинаковые входы, разный результат» — это уже чисто арифметика/округление/окна.

5) Быстрый sanity-check оконных «prev/next» прямо в каждой таблице

(покажет, соответствует ли «prev» реальному LAG() и «next» — LEAD() именно внутри самой таблицы.)

-- v1
WITH s AS (
  SELECT calculation_code, dt_valid_from,
         average_weighted_stock_price_rule2_prev_date_amount AS r_prev,
         average_weighted_stock_price_rule2_next_date_amount AS r_next,
         LAG(average_weighted_stock_price_rule2_prev_date_amount)
           OVER (PARTITION BY calculation_code ORDER BY dt_valid_from) AS lag_prev,
         LEAD(average_weighted_stock_price_rule2_next_date_amount)
           OVER (PARTITION BY calculation_code ORDER BY dt_valid_from) AS lead_next
  FROM userdata.material_price_calculation
)
SELECT
  COUNT(*) FILTER (WHERE r_prev IS DISTINCT FROM lag_prev) AS prev_mismatch,
  COUNT(*) FILTER (WHERE r_next IS DISTINCT FROM lead_next) AS next_mismatch
FROM s;

-- v2 (аналогично)


Если одна версия даёт нули, а другая — нет, алгоритм окна действительно разный.

6) Если всё выше «чисто» — проверь «скрытое» отличие в порядке вычислений

Иногда меняют местами шаги: сначала усреднение, потом деление на peinh vs сначала деление, потом усреднение. Это даёт микродельты.

Проверь, исчезают ли дельты, если обе стороны привести к единой канонической формуле (например, «сначала всё в базовые единицы, потом агрегаты», и округлять в самом конце):

WITH canon_v1 AS (
  SELECT calculation_code, dt_valid_from,
         ROUND(COALESCE(standard_price_amount,0)::numeric, 12) AS stprs_canon
  FROM userdata.material_price_calculation
),
canon_v2 AS (
  SELECT calculation_code, dt_valid_from,
         ROUND(COALESCE(standard_price_amount,0)::numeric, 12) AS stprs_canon
  FROM userdata.material_price_calculation_v2
)
SELECT COUNT(*) FILTER (WHERE ABS(v1.stprs_canon - v2.stprs_canon) > 1e-9) AS n_diff_canon
FROM canon_v1 v1 JOIN canon_v2 v2 USING (calculation_code, dt_valid_from);


Если n_diff_canon = 0, но «сырые» отличались — вопрос в месте/этапе округления.
