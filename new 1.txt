Критичные требования к переходу на dbt

На текущем этапе выявлены четыре принципиальных недостатка предлагаемого решения. До их устранения массовое переключение сущностей на dbt в PROD несёт
риски.

 1. Единый репозиторий для dbt-решения

   Текущее состояние

  Компоненты одной dbt-сущности находятся в разных репозиториях:

  - модели, тесты и остальные dbt-компоненты — в dbt-репозитории;
  - YAML с расписанием, параметрами запуска и настройками ClickHouse — в ETL-репозитории.

  Таким образом, одно логическое изменение требует синхронных изменений и релизов двух репозиториев.

   Риски


  - Несовместимые версии dbt-моделей и YAML-конфигурации.
  - Один MR может быть выпущен, а второй — задержан или завершён ошибкой.
  - Усложняется определение полного состава релиза.
  - Откат необходимо синхронно выполнять в двух репозиториях.
  - Затрудняется связь задачи YouTrack со всеми изменениями сущности.
  - После завершения миграции в legacy ETL-репозитории остаётся часть конфигурации нового решения.
  - Повышается вероятность ошибок при сопровождении и передаче ответственности.

   Требование

  Все компоненты новой dbt-реализации должны иметь единый источник истины и храниться в dbt-репозитории:

  - dbt-модели;
  - тесты;
  - конфигурация сущностей;
  - настройки расписаниялогика Airflow-оркестрации dbt;
  - объектные настройки ClickHouse;
  - миграционные инструкции;
  - правила валидации и релиза.

  ETL-репозиторий должен использоваться только для legacy-расчётов на время переходного периода.


 2. Исключение ClickHouse-объектов из общего YAML сущности

   Текущее состояние

  Общий YAML сущности содержит список всех dbt-моделей и соответствующих ClickHouse DAG:

  clickhouse:
    tables:
      - dag_name: dm_ka_personnel_meta
        dbt_model: dm_s_personnel
      - dag_name: dm_kaizen_submitted_meta
        dbt_model: dm_s_kaizen_submitted

  С одной сущностью одновременно могут работать несколько инженеров. При добавлении, удалении или переименовании разных моделей они изменяют один файл.

   Риски
	 - нету обработки на лету
  - Регулярные Git-конфликты.
  - При разрешении конфликта можно случайно удалить изменение другого инженера.
  - Удаление одной модели может затронуть настройки другой.
  - Общий YAML становится точкой блокировки параллельной разработки.
  - С ростом количества таблиц файл становится сложным для проверки и сопровождения.
  - Невозможно независимо выпускать объектные изменения.

   Требование

  В YAML сущности должны остаться только общие параметры:

  - имя и идентификатор сущности;
  - расписание логика;
  - общий dbt selector;
  - внешние зависимости;
  - общие параметры выполнения;
  - настройки уведомлений.

  Настройки ClickHouse необходимо хранить на уровне конкретной модели или генерировать из dbt metadata.

  

   3. Недостаточная детализация Airflow DAG

   Текущее состояние

  В Airflow создаётся отдельный DAG на сущность, но весь набор dbt-моделей запускается одной задачей:

  run_dbt = dbtBashOperator(
      task_id=f"run_dbt_{entity_name}",
      dbt_command=config["dbt"]["dbt_command"],
      additional_vars=config["dbt"]["additional_vars"],
  )

  Команда запускает все модели сущности:

  dbt run --select tag:ENTITY

  В интерфейсе Airflow вся сущность представлена одной задачей.

  Ограничения

  Airflow не показывает на графе:

  - какая модель сейчас выполняется;
  - какая конкретно модель завершилась ошибкой;
  - какие модели уже успешно рассчитаны;
  - какая физическая таблица была изменена;
  - какую модель необходимо перезапустить;
  - после какой модели можно запускать соответствующую выгрузку в ClickHouse.

  Подробности могут присутствовать во внутренних логах dbt, но они не предоставляют привычного объектного управления через Airflow.

  Риски

  - Падение одной модели приводит к ошибке всей задачи. 
  - При повторном запуске может пересчитываться вся сущность.
  - Уже успешные модели могут выполняться повторно.
  - Несколько таблиц могут успеть изменить данные до падения.
  - Сущность остаётся в частично рассчитанном состоянии.
  - Оператору сложнее определить точку сбоя.
  - Невозможно стандартным способом перезапустить только проблемную таблицу.
  - Сложно организовать точную зависимость между моделью и ClickHouse DAG.
  - Невозможно контролировать SLA и длительность отдельных моделей.


  Airflow при этом показывает только одну упавшую задачу сущности, хотя состояние отдельных таблиц различается.

  Требование

  Airflow должен предоставлять наблюдаемость и управление на уровне dbt-модели либо операционной группы моделей.


  Граф желательно формировать автоматически на основании dbt manifest, чтобы не дублировать зависимости вручную.

  Пример:

  dbt_entity
  ├── model_A
  │   ├── run
  │   ├── test
  │   └── clickhouse_A
  │
  ├── model_B
  │   ├── run
  │   └── test
  │
  └── model_C
      ├── run
      ├── test
      └── clickhouse_C

 

  4. Отсутствие интеграции с SAP OData

   Текущее состояние

  В существующем ETL framework каждый сервис SAP OData загружается отдельным Airflow DAG.

  Если данные сервиса используются в сущности, перед расчётом устанавливается sensor, который ожидает успешное завершение соответствующего SAP OData DAG.

  Таким образом, текущий граф явно выражает зависимость:

  SAP OData DAG
        ↓
  Airflow sensor
        ↓
  Расчёт зависимых таблиц сущности

  В представленном dbt DAG такая интеграция отсутствует. Сущность запускается только по собственному расписанию.

   Риски

  - dbt может начать расчёт до завершения SAP OData.
  - Модель может использовать данные предыдущего периода.
  - Возможен расчёт на частично загруженном источнике.
  - Airflow покажет успешный dbt run, хотя входные данные были неактуальны.
  - Расхождения могут быть обнаружены только аналитиком после публикации витрины.
  - Некорректные данные могут быть переданы в ClickHouse.
  - При повторном запуске SAP OData зависимые dbt-модели автоматически не пересчитаются.

- расчет сап одаты не должен затрагвать 



  Перед запуском зависимых dbt-моделей sensor должен проверить:

  - успешное завершение SAP OData DAG;
  - соответствие требуемому бизнес-периоду;
  - отсутствие частичной загрузки;
  - актуальность загрузки относительно текущего запуска сущности.

  Если разные модели сущности зависят от разных SAP-сервисов, зависимость желательно задавать на уровне модели:

  model: dm_s_kaizen_personnel_involvement

  upstream:
    - type: sap_odata
      dag_id: sap_odata_personnel

  Тогда независящие от SAP модели не будут без необходимости ожидать всю внешнюю загрузку.


Процесс релиза в дбт отличается от текущего, нет привязки задачи к объектам не сохрняется информация как у нас в таблицы tech_etl.release_log,  tech_etl.release_backup_registry

Нет автоматизации для ручных таблиц - это котоорые грузятся через инкремент и еще они у них не бэкапятся перед релизом что делается в етл
