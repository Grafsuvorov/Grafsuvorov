1. tech_etl.yt_incidents
  Это главная таблица инцидентов.
  В ней хранится текущий срез карточки: кто создал, что сломалось, по какой таблице, кто чинит, в каком статусе сейчас.

  Зачем нужна:

  - строить UI по инцидентам
  - искать инциденты по таблице/сущности
  - делать отчеты по направлениям, командам, исполнителям
  - связывать инцидент с объектом КХД

  Поля:

  - issue_id
      - внутренний технический id карточки в YouTrack
      - нужен как стабильный ключ
  - issue_key
      - человекочитаемый номер, например DWH-14322
      - нужен для поиска и ссылок
  - issue_type
      - тип карточки
      - у вас здесь обычно будет Incident
  - project_name
      - проект YouTrack, например КХД
  - summary
      - заголовок карточки
      - например: dq_all0001. Дубликаты по ключу. dm.sales_account_receivables
  - description_text
      - основное описание карточки
      - общий текст, который пользователь видит в описании
  - state_name
      - текущий статус
      - например: Зарегистрирована, В работе, Завершена
  - priority_name
      - приоритет
      - например: Normal
  - author_name
      - кто создал инцидент
  - assignee_name
      - кто сейчас исполнитель
  - team_name
      - команда / подсистема
      - например SA (System Analytics), DE (Data Engineer)
  - direction_name
      - направление
      - например Сбыт
  - dashboard_name
      - дашборд / бизнес-направление, если поле есть
      - полезно для аналитики по источнику проблемы
  - component_name
      - компонент, если в карточке используется такое поле
  - incident_reason_name
      - причина инцидента
      - например Человеческий фактор
  - trigger_dttm
      - время триггера алерта
  - incident_start_dttm
      - время начала сбоя
  - detected_dttm
      - когда инцидент обнаружили
  - work_finished_dttm
      - когда работы по инциденту завершились
  - entity_name
      - название сущности из карточки
      - если его указали
  - table_name_raw
      - как таблица пришла из YouTrack
      - например dm.sales_account_receivables
  - table_schema
      - схема, выделенная из table_name_raw
      - например dm
  - table_name
      - имя таблицы без схемы
      - например sales_account_receivables
  - object_fqn
      - полное имя объекта в виде schema.table
      - это главное поле для привязки к объекту приложения
  - event_description
      - описание события / формулировка проблемы
      - например: Дубликаты по ключу dm.sales_account_receivables
  - alert_source
      - откуда пришел алерт
      - например ссылка на DQ dashboard или Алертинг пульс
  - root_cause
      - причина возникновения из блока Анализ
  - fix_actions
      - действия по устранению из блока Анализ
  - preventive_actions
      - проактивные мероприятия из блока Анализ
  - spent_time_text
      - поле Spent time как есть текстом
  - actual_effort_text
      - фактические трудозатраты как есть текстом
  - estimated_effort_text
      - оценка трудозатрат как есть текстом
  - ai_saving_text
      - экономия за счет ИИ, если это поле есть
  - created_at_yt
      - когда карточка создана в YouTrack
  - updated_at_yt
      - когда карточка последний раз обновлялась
  - resolved_at_yt
      - когда карточка была переведена в завершенное состояние, если получится вытащить
  - raw_json
      - полный JSON карточки
      - нужен на случай, если потом захотите распарсить дополнительные поля
  - dttm_loaded
      - когда запись загрузили в БД
  - dttm_updated
      - когда запись в БД в последний раз обновили

  2. tech_etl.yt_incident_links
  Это таблица связей инцидента с другими задачами.

  Зачем нужна:

  - понять, какие задачи были заведены для исправления инцидента
  - видеть хотфиксы, дочерние задачи, связанные доработки
  - строить цепочку инцидент -> задачи на исправление

  Поля:

  - issue_id
      - id самого инцидента
  - issue_key
      - номер самого инцидента
  - linked_issue_id
      - id связанной карточки
  - linked_issue_key
      - номер связанной карточки
      - например DWH-13721
  - linked_issue_type
      - тип связанной карточки
      - например Task, Incident, Bug
  - linked_issue_summary
      - заголовок связанной карточки
  - link_type
      - тип связи
      - например:
          - родитель для
          - relates to
          - subtask of
  - dttm_loaded
      - когда эта связь загружена

  ———

  3. tech_etl.yt_incident_history
  Это таблица истории жизни инцидента.

  Зачем нужна:

  - видеть комментарии
  - видеть смену статусов
  - видеть смену исполнителя
  - видеть изменение трудозатрат
  - строить timeline инцидента

  Поля:

  - issue_id
      - id инцидента
  - issue_key
      - номер инцидента
  - event_dttm
      - когда произошло событие
  - author_name
      - кто сделал изменение или написал комментарий
  - event_type
      - тип события
      - например:
          - comment
          - field_change
          - worklog
          - link_change
  - field_name
      - какое поле изменили
      - например:
          - Состояние
          - Исполнитель
          - Фактические трудозатраты
  - old_value
      - старое значение поля
  - new_value
      - новое значение поля
  - comment_text
      - текст комментария, если это комментарий
  - dttm_loaded
      - когда это событие загрузили в БД

  ———

  Как они работают вместе

  yt_incidents

  - основная карточка инцидента
  - текущее состояние

  yt_incident_links

  - показывает, с какими задачами этот инцидент связан

  yt_incident_history

  - показывает, как инцидент жил во времени

  Пример:

  - в yt_incidents:
      - инцидент по dm.sales_account_receivables
      - автор Karimova Diana
      - статус В работе
  - в yt_incident_links:
      - связи на DWH-14322, DWH-13721
  - в yt_incident_history:
      - комментарии аналитиков
      - смена исполнителя
      - рост трудозатрат с 5м до 7ч 5м

  ———

  Почему не одна таблица
  Потому что:

  - у одного инцидента может быть много связанных задач
  - у одного инцидента может быть много комментариев и изменений
  - если всё хранить в одной таблице, будут дубли и кривая аналитика

  ———
