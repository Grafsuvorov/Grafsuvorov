# Prototype Review: рабочий процесс

## 1. Аналитик: подготовка и запуск

Аналитик создаёт задачу через страницу **Prototype Review**. Перед запуском он указывает ссылку или номер своего MR, описание изменения и особенности загрузки, направление, ключевые поля, дату релиза, связанные задачи и комментарии.

Если таблица должна использоваться несколькими сущностями загрузки, их нужно указать через запятую, например: `MANAGEMENT_REPORTING_1, MANAGEMENT_REPORTING_2`.

В аналитическом MR должны находиться SQL-скрипты изменения таблицы. Скрипты могут быть одним файлом либо отдельными файлами `recreate` и `insert`: Prototype Review объединит их в один объект проверки.

После запуска Prototype Review:

- проверяет SQL и объект в DEV;
- определяет целевую таблицу, зависимости, ключи и потенциальные проблемы;
- назначает новый уникальный `table_id` для нового metadata-объекта;
- создаёт YouTrack-задачу;
- создаёт ветку и MR в ETL-репозитории с `meta_data_file.yaml`;
- создаёт отдельный YAML для каждой указанной сущности;
- создаёт MR в dbt-проекте с SQL таблиц и Greenplum VIEW, настройками registry и DQ для таблиц.

SQL представлений публикуется даже без изменений DQ, по пути `dbt_greenplum_elt/models_metadata/<schema>/<schema>.<view>.sql`. Для VIEW не создаются registry с unique_key и DQ duplicates/nulls. Пропуск выполнения в DEV не отменяет публикацию SQL. ClickHouse views остаются в своём контуре и не публикуются как Greenplum SQL в dbt. Если SQL выбранного Greenplum VIEW не найден в diff, публикация dbt возвращает явную ошибку вместо пропуска объекта.

Prototype Review передаёт в ETL MR только YAML. Скрипты `recreate`, `insert` и `truncate` автоматически не публикуются: их создаёт и сопровождает инженер.

## 2. Инженер: проверка и реализация

Инженер получает задачу из YouTrack и:

1. Проверяет созданные ветку и MR в ETL-репозитории.
2. Проверяет YAML: схему, таблицу, сущность, `table_id`, зависимости `depends_on`, пути к SQL и параметры загрузки.
3. Изучает MR аналитика и выполняет его SQL в DEV.
4. При необходимости оптимизирует SQL, структуру таблицы, распределение, индексы и логику загрузки.
5. При неполной загрузке использует описание аналитика, чтобы определить условия обновления. Если информации недостаточно, уточняет требования у аналитика до реализации.
6. Создаёт или обновляет инженерные SQL-файлы в папке таблицы:
   - `sql_query_recreate_init.sql`;
   - `sql_query_insert_init.sql`;
   - `sql_query_truncate.sql`, если требуется.
7. Обновляет YAML, если изменились параметры загрузки, зависимости, ключи или сущности.
8. Добавляет изменения в релизный план.

Если объект используется несколькими сущностями с одним алгоритмом, SQL-файлы принадлежат основной сущности. YAML остальных сущностей ссылаются на эти общие SQL-файлы.

### Разные алгоритмы одной таблицы

Если несколько файлов MR записывают в одну физическую таблицу, Prototype Review останавливается перед выполнением SQL и предлагает сопоставление:

- **Общий алгоритм** — файлы выполняются вместе, YAML нескольких сущностей используют SQL первой сущности.
- **Разные алгоритмы** — каждому файлу назначается своя сущность. Например, `dm.sb_wuc.sql` → `SB_WUC`, а `dm_update.sb_wuc.sql` → `2HOURS`, хотя оба INSERT пишут в `dm.sb_wuc`. Несколько файлов с одинаковым набором сущностей образуют один алгоритм.

Сущности можно выбрать из metadata или ввести вручную. Одна сущность не может принадлежать разным алгоритмам. Все файлы должны быть сопоставлены. Общие DDL и TRUNCATE-файлы включаются в каждую проверку.

Алгоритмы выполняются последовательно: сначала SQL первого алгоритма и его проверки строк/дублей, затем следующего. Поэтому результат первого алгоритма фиксируется до перезаписи таблицы вторым. При изменении ключей или сопоставления необходимо повторить проверку алгоритмов.

В инженерном MR для отдельных алгоритмов сохраняются собственные YAML и изменённые SQL в каталогах соответствующих сущностей. INSERT одного алгоритма не ссылается на INSERT другого. Существующие общие ссылки на DDL/TRUNCATE сохраняются, если этих скриптов нет в MR. В dbt SQL алгоритмов сохраняется раздельно, например `models_metadata/dm/_variants/SB_WUC/dm.sb_wuc.sql` и `models_metadata/dm/_variants/2HOURS/dm.sb_wuc.sql`. Registry и DQ остаются общими для физической таблицы; конфликтующие DQ/SCD-настройки останавливают создание задачи.

## Режим ОХД / dbt

На странице Prototype Review выберите плитку **«ОХД · dbt»**. Переключение режима очищает MR, результаты, сопоставление алгоритмов и параметры задачи, чтобы данные разных хранилищ не смешивались.

В ОХД SQL выполняется через уже используемое подключение `DBT_LOGS_DATABASE_URL`. Необязательная переменная `OHD_DEV_DATABASE_URL` переопределяет его для Prototype Review. Если оба подключения отсутствуют, выполнение останавливается; подключение `DEV_DATABASE_URL` КХД не подставляется. Существующие ключи, сущности, SCD и DQ берутся из registry dbt-проекта ОХД в `main`. Для новых объектов ключи задаются в форме; сущность ОХД не требуется. Доступны повторный запуск отдельных объектов и сопоставление нескольких алгоритмов одной таблицы.

В режиме ОХД зависимости из SQL не извлекаются: ни при выполнении и повторной проверке, ни при создании задачи и публикации dbt. Объекты не переставляются по графу зависимостей и не отмечаются устаревшими по найденным upstream-связям. Проверка изменения самих SQL-файлов сохраняется.

Задача создаётся в проекте YouTrack ОХД. Публикация формирует только dbt MR в `main`: SQL и registry в `dbt_greenplum_elt/models_metadata/<schema>/`, технические DQ в `dbt_greenplum_elt/models/dq/technical/`. Имена файлов нормализованы, физические имена и ключи с `/bic/` сохраняются в YAML. Целевой объект определяется SQL, а не произвольным именем исходного файла. ETL YAML, `table_id`, ETL workspace и инженерный MR в этом режиме не создаются. STG-загрузка доступна в обоих контурах, ClickHouse — в КХД.

ОХД использует отдельный GitLab. В серверном `.env` явно задайте:

```dotenv
OHD_GITLAB_API_URL=https://ohd-gitlab.example/api/v4
OHD_GITLAB_TOKEN=значение_созданного_токена
OHD_GITLAB_SSL_VERIFY=true
OHD_ANALYST_GITLAB_PROJECT=namespace/analysts-project
OHD_DBT_GITLAB_PROJECT=namespace/engineers-dbt-project
```

В `OHD_GITLAB_TOKEN` нужно значение Personal Access Token, созданного под именем `ohd_app_token`, а не само имя. Этот токен по умолчанию используется для чтения MR аналитиков и публикации в dbt. Необязательные `OHD_ANALYST_GITLAB_TOKEN` и `OHD_DBT_GITLAB_TOKEN` позволяют переопределить токены отдельно. Проекты указываются путями `namespace/project` из URL или числовыми ID, не отображаемыми названиями. Адрес API, проекты, токены и SSL-настройка КХД в ОХД не подставляются. Все запросы — MR, SQL, registry, ветки, коммиты и dbt MR — используют GitLab ОХД. Ссылка на MR другого сервера отклоняется до чтения файлов и выполнения SQL.

Для базы по-прежнему используется существующий `DBT_LOGS_DATABASE_URL`; `OHD_DEV_DATABASE_URL` может переопределить его. В YouTrack отдельно задаются `OHD_YOUTRACK_QUEUE` и `OHD_YOUTRACK_PROJECT_ID` или точное название `OHD_YOUTRACK_PROJECT`. Также доступна `OHD_YOUTRACK_DIRECTION_FIELD_NAME`. Шаблоны GitLab-настроек добавлены в `.env`, `.env.production` и `.env.example`, переменные объявлены в `api/config.py`. Docker Compose читает `.env` через `env_file`; после заполнения настроек обновите и пересоздайте контейнер API.

## 3. Тестирование аналитиком

После выполнения инженерных работ задача передаётся аналитику. Аналитик проверяет данные в DEV, полноту загрузки, бизнес-логику, соответствие постановке и влияние на зависимые витрины и отчёты.

Замечания фиксируются в YouTrack. Инженер вносит корректировки до подтверждения результата.

## 4. Проверка dbt

Инженер проверяет ветку dbt-проекта:

1. Просматривает изменения registry и DQ-моделей.
2. Проверяет `unique_key`, SCD-настройки и DQ-условия.
3. Прогоняет все изменённые dbt-модели и связанные тесты.
4. Убеждается, что проверки не создают ложных ошибок.
5. Подготавливает ETL- и dbt-ветки к релизу после успешных проверок.

## 5. Meta Workspace

Перед передачей в релиз инженер в **Meta Workspace** запускает проверки для своей ветки. Необходимо убедиться в валидности YAML, корректности путей к SQL, отсутствии конфликтов `table_id`, корректности зависимостей и согласованности ETL metadata с dbt.

Только после успешного прохождения этих проверок ветка считается готовой к релизу.

## 6. Релиз

После согласования изменения попадают в релизный процесс и затем в `main` согласно принятому процессу команды.

Релизный менеджер запускает CI/CD после merge, проверяет статусы всех этапов pipeline, анализирует ошибки и warnings. Простые проблемы устраняет самостоятельно, для предметных проблем привлекает инженера, ответственного за задачу.

Когда pipeline завершён успешно и критичных ошибок нет, начинается релиз.


## STG-загрузка в несколько сущностей

Наличие физической таблицы в DEV без YAML в main Git допустимо: таблицу могли создать вручную. При запуске STG-функции приложение генерирует недостающий YAML. Для каждой сущности сохраняется существующий `table_id` из каталога metadata; если записи нет, используется новый ID. Физическое наличие таблицы не определяет наличие metadata. Ошибки доступа к Git и конфликты ID продолжают останавливать генерацию.

Для каждой выбранной сущности формируется собственный `meta_data_file.yaml`:

- `entity_name` записывается обычным YAML-значением без принудительных JSON-кавычек для имён расписаний;
- `entity_id` каждый раз проверяется по имени в `entities_meta`, значение первого YAML не копируется;
- существующий `table_id` определяется для конкретных `entity_id + table_schema + table_name` в `tables_meta`; при отсутствии записи сохраняется ID из main Git;
- для новой metadata-записи выделяется отдельный `table_id` из sequence, ID первого расписания не распространяется на остальные;
- подготовленные YAML передаются через `yaml_contents` от предпросмотра до создания MR, чтобы повторно не выделять ID.

SQL хранится в каталоге первой сущности, дополнительные YAML сохраняют ссылки на эти SQL. В форме можно раскрыть YAML каждой сущности. Одинаковые `table_id` у выбранных сущностей, ID чужого объекта и неизвестная сущность останавливают подготовку. Если после предпросмотра изменились target или набор сущностей, нужно повторить генерацию. Правила одинаковы для отдельной STG-задачи и для STG-загрузки в составе общего Prototype Review.


## Диагностика подключения ОХД

Создание задач ОХД использует схему проекта `0-83` (`SDS`), подтверждённую ручным созданием `SDS-543`, `SDS-546` и `SDS-547`: оценка `173-515` — числовое поле, направление `173-646` — текстовое поле, тип карточки `134-1948` — enum `Task`. Список административных полей и задача-образец для этого не нужны; `OHD_YOUTRACK_REFERENCE_ISSUE` больше не используется. При пустом `OHD_YOUTRACK_PROJECT_ID` применяется `0-83`; явно заданный другой ID остановит создание, чтобы не отправлять чужие ID полей. Значения направления берутся из формы; при `YOUTRACK_DEFAULT_ESTIMATE_MINUTES=60` числовая оценка равна `1`. Поля исполнителя `135-769` и даты релиза `173-517` заполняются, когда соответствующие данные заданы. Схема вынесена в `api/services/prototype_review_youtrack_ohd.py`; при переносе на другой проект её нужно обновить. В логах источник отмечается `[YTRACK FIELDS] source=verified_ohd`, оценка — `[YTRACK ESTIMATE]`.

Для обращений к YouTrack в режиме ОХД обязателен отдельный `OHD_YOUTRACK_TOKEN`. Укажите реальное значение в серверном `.env`. Токен используется для чтения родительской задачи, создания задачи, связей, вложений и комментариев с MR. При пустом значении приложение выдаёт ошибку настройки; `YOUTRACK_TOKEN` используется только для КХД. URL и настройки SSL YouTrack остаются общими. После изменения пересоздайте API: `docker compose up -d --force-recreate api`.

Если проект YouTrack не находится по имени, запустите из корня репозитория `python3 scripts/ytrack_find_project.py --issue SDS-471`. Скрипт использует `YOUTRACK_URL`, `OHD_YOUTRACK_TOKEN` (для `--mode khd` — `YOUTRACK_TOKEN`) и `YOUTRACK_SSL_VERIFY` из окружения или `.env`; непустой `SCRIPT_YOUTRACK_TOKEN` в начале скрипта имеет приоритет. Скрипт читает проект непосредственно из доступной задачи и печатает `OHD_YOUTRACK_PROJECT`, `OHD_YOUTRACK_PROJECT_ID` и `OHD_YOUTRACK_QUEUE`. Внешние изменения не выполняются. Для другого файла настроек используйте `--env-file .env.production`; для поиска по названию — `--project "ОХД"`, для всех доступных проектов — `--list`, для настроек КХД — `--mode khd`. Список проектов читается с пагинацией; доступ к задаче и доступ к административному списку проектов могут различаться.

В режиме ОХД поле «Сущность загрузки» в карточке объекта отсутствует и не требуется для ревью или создания задачи. Для новых объектов registry формируется без `relation.entity`; ранее сохранённые значения registry сохраняются при обновлении. Для КХД правила заполнения сущности остаются прежними.

Перед запуском ревью ОХД и отдельной проверкой таблицы приложение выполняет read-only SELECT с получением имени базы, пользователя, адреса и порта сервера. В логах API сообщения имеют метку `[OHD DB CHECK]`: `START` показывает параметры настройки и её источник (`OHD_DEV_DATABASE_URL` либо резервный `DBT_LOGS_DATABASE_URL`), `OK` — фактическое подключение и длительность, `FAILED` — причину ошибки. Пароль и полная строка подключения не выводятся. Тайм-аут установления соединения — 5 секунд.

При неудаче ревью останавливается до выполнения SQL объектов. Успешное подключение само по себе не подтверждает права на CREATE, DROP или INSERT.

## Регистр физического имени таблицы

`table_name` в YAML сохраняет регистр исходного имени, например `s1c_SI_AluminaRemains_AI`. Поиск metadata и каталоги SQL в Git могут оставаться нормализованными (`s1c_si_aluminaremains_ai`): это разные представления имени. Prototype Review восстанавливает регистр quoted-идентификатора из SQL и сохраняет его при обновлении YAML, валидации и смене/добавлении сущности. Уже сохранённое смешанное имя не заменяется нормализованным ключом поиска. Правило не выделяет новые `table_id`/`entity_id`.

## Повторный запуск отдельных объектов

После исправления SQL в исходном MR нажмите **«Перезапустить SQL и проверки»** в карточке объекта или **«Перезапустить объекты с ошибками»** для группы. Приложение читает свежие файлы MR и запускает только выбранные объекты. Для нескольких алгоритмов одной таблицы повторяется только выбранный алгоритм; строки и дубли проверяются сразу после его выполнения. Значения ключей из формы передаются в повторную проверку.

Результаты остальных объектов и комментарии/настройки аналитика сохраняются. Старые ошибки выбранных объектов заменяются новыми результатами. Если изменён SQL другого объекта или повторно выполнен его upstream, результат такого объекта отмечается как устаревший. Он не запускается автоматически; для создания задачи нужно перепроверить отмеченные объекты. Изменение состава объектов MR требует полного запуска. При создании задачи backend дополнительно сравнивает SQL с сохранённым отпечатком проверенной версии.

Повторный запуск выполняет SQL целиком для выбранного объекта, включая предусмотренную подготовку таблицы. Если предварительная очистка завершилась ошибкой, INSERT не выполняется. Успешные результаты сохраняются в текущей открытой форме; обновление страницы их не восстанавливает.


## Несколько STG-таблиц и общий diff

На странице Prototype Review в выбранном контуре нажмите **«+ Добавить STG-таблицу»** для каждой таблицы. У каждой карточки свои источник, target, сервер, ключи, SQL/YAML и статус. КХД поддерживает несколько сущностей каждой таблицы; в ОХД сущность не запрашивается. **«Сгенерировать непроверенные»** запускает выбранные неготовые карточки последовательно. Успешные карточки сворачиваются, их результаты сохраняются при генерации соседних. Кнопка **«Параметры и SQL»** раскрывает карточку; изменение её параметров сбрасывает только её готовность. Повторный запуск функции пересоздаёт соответствующий объект в DEV.

Для одной задачи по STG и diff укажите MR, запустите review, подготовьте выбранные STG-таблицы и заполните общие параметры задачи под результатами diff. Перед созданием показывается состав общей задачи: количество объектов diff и полный список выбранных STG. Все выбранные STG включаются автоматически; для исключения снимите флажок в карточке таблицы. Создание блокируется, пока выбранная таблица не готова или цели повторяются. Для задачи только по STG оставьте MR пустым и заполните общие параметры под списком STG. Задача создаётся одна на выбранный набор.

В КХД YAML/SQL всех выбранных STG-таблиц сохраняются в той же ветке и инженерном MR, что и объекты diff. Кроме того, dbt MR включает SQL, registry и DQ всех этих STG-таблиц, с сохранением их сущностей; прежде в dbt передавались только объекты diff. В ОХД генерация, список серверов и физических таблиц используют `OHD_DEV_DATABASE_URL` / `DBT_LOGS_DATABASE_URL`, без обращения к каталогу metadata КХД. Предполагаются функция `tech_etl.etl_source_to_greenplum_new` и каталог `tech_etl.source_servers_meta` в базе ОХД. В dbt MR попадает отдельный канонический SQL вызова функции и registry/DQ каждой STG-таблицы, вместе с SQL и registry объектов diff. Дополнительный INSERT после вызова функции не добавляется, поскольку функция уже выполняет первоначальную загрузку. ETL YAML и ID metadata в ОХД не создаются.

API принимает `source_loads` — массив подготовленных STG-объектов. Старое поле `source_load` остаётся для совместимости; оба поля одновременно передавать нельзя. Проверяются контур, успешный статус генерации, SQL, первичный ключ, дубли целей внутри набора, пересечение с объектами diff и удаляемыми объектами. Изменения в DEV выполняются только явной генерацией; публикация задачи сама не перезапускает функцию. Результаты генерации хранятся в открытой странице и теряются при её обновлении или смене контура.


### Автоподстановка существующего STG target

При вводе или выборе имени target приложение автоматически проверяет конкретную таблицу после короткой паузы. Регистр при поиске не учитывается; в форме и генерируемых данных сохраняется физическое имя из DEV. Поля, ключ, параметры источника и сервер подставляются, когда они доступны. Отдельной кнопки подстановки нет. В КХД параметры читаются из существующего ETL YAML/SQL, в ОХД — из YAML registry и SQL модели в dbt main; вручную созданная таблица без файла остаётся допустимой. Список полей берётся из YAML (`fields`, `fields_list`, `source_fields` или `source_fields_list`, строка либо список), затем из `v_fields_list` сохранённого SQL загрузки для старых YAML. Колонки физической DEV-таблицы для этого не используются. Если сохранённого списка нет, остаётся `ALL`, что явно указано в форме. Новая генерация КХД сохраняет выбранный список в `fields` YAML. Запоздавший ответ не применяется после смены target; ручные правки во время запроса не заменяются автоматически.

Список подсказок и проверка точного имени независимы. Сбой загрузки подсказок показывается отдельно; введённая таблица проверяется адресно. Чтение колонок и первичного ключа выполняется через `pg_catalog` без подсчёта размеров физических таблиц. Ошибка endpoint списка записывается в лог API с меткой `[SOURCE TABLES]`; сообщения `table sizes cache` относятся к другой фоновой задаче.


Перед созданием клиент передаёт `expected_source_load_count`. Несовпадение с принятым сервером массивом STG останавливает создание задачи. Ответ содержит `task_contents` с целями diff и STG; клиент предупреждает, если сервер не подтвердил включение выбранных STG (например, при переносе только части обновлённых файлов). В логах состав принятой задачи отмечается `[PROTOTYPE TASK CONTENTS]`. Подтверждение состава не заменяет проверку ошибок публикации отдельных MR.


### Явное создание общей задачи

После подготовки STG и проверки MR нажмите **«Создать общую задачу · STG: 2 · diff: 1»** (числа соответствуют текущему составу). Одинаковая кнопка доступна под STG-таблицами и внизу результатов ревью; рядом перечислены все цели STG и diff. Выбранные таблицы читаются непосредственно из карточек в момент нажатия. Общие параметры, введённые до добавления MR, переносятся в общую форму. После успешного создания кнопки блокируются, рядом остаётся ссылка на созданную задачу.

Для общей задачи используется отдельный `POST /api/admin/prototype-review/create-combined-issue`, с обязательными массивом STG и ожидаемым количеством. Без STG, MR или проверки имеющихся объектов diff задача не создаётся. Старый API без маршрута вернёт ошибку до создания задачи; интерфейс не переключается на создание задачи только по diff. Поэтому при ручном обновлении обязательно перенесите и frontend, и `api/routers/prototype_review.py`, `api/schemas/prototype_review.py`, `api/services/prototype_review_issue_workflow.py`. Все кнопки создания STG/diff вызывают один обработчик страницы: состав определяется текущими выбранными карточками и проверенным MR, а не расположением кнопки. Если MR введён, но ещё не проверен, создание блокируется; создать из этой же формы задачу только по STG в обход MR нельзя. Без MR этот же обработчик создаёт задачу только по выбранным STG.
