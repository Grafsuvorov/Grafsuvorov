  docker exec -it table-dependency-viewer-frontend-1 sh -c "grep -R \"\\/h\\/auth\\/login\\|\\/h\\/auth\\|VITE_API_BASE_URL\\|auth/login\" /usr/share/nginx/html/assets
  | head -50"

  2. Посмотри, какой build реально лежит в контейнере:

  docker exec -it table-dependency-viewer-frontend-1 sh -c "ls -lah /usr/share/nginx/html/assets"

  3. Проверь API routes без отступов:

  docker exec -it table-dependency-viewer-api-1 sh -c "python - <<'PY'
  from api.main import app
  for r in app.routes:
      if '/auth' in r.path:
          print(r.path, sorted(r.methods))
  PY"

  4. Проверь прямо в браузере, какой js-файл грузится.
     У тебя уже видно:

  - index-BDovko37.js

  Значит браузер/сервер сейчас отдает конкретный старый bundle. Нужно понять, есть ли в контейнере уже новый hash или все еще старый.

  Что я думаю сейчас

  - backend auth, скорее всего, уже есть
  - но frontend отдает старый bundle, в котором base URL = /h
  - поэтому запрос идет в /h/auth/login

  Почему это могло “сломаться само”

  - старый dist/старый image
  - браузерный cache
  - frontend не пересобрался из актуального кода/env
  - nginx отдает не тот build

  Что сделать почти наверняка

  После проверки выше, если в assets найдется /h/auth/login, пересобери frontend совсем с нуля:

  docker compose build --no-cache frontend
  docker compose up -d frontend
  docker image prune -f

  И потом открой страницу в браузере через hard refresh:

  - Ctrl+F5 / Shift+Reload

  Если хочешь, после вывода grep по assets я скажу уже точно, откуда берется /h.
