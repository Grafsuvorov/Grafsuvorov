Это нужно добавить в Story 3 «Объектная наблюдаемость и перезапуск в Airflow». Алертинг — часть наблюдаемости: уведомление должно объяснять, какой объект упал,
  насколько он критичен и что делать оператору.

  Внутри Story лучше создать отдельную задачу:

  > DBT: реализовать объектный и приоритизированный алертинг по ошибкам моделей                                                                                        

  ### Проблема

  Текущее уведомление содержит только техническую ошибку общей Airflow-за-задачи:

  DAG: dq
  Task: dbt_task
  Error: Bash command failed
  Exit code: 1

  По такому сообщению невозможно определить:

  - какая dbt-модель упала;
  - какая физическая таблица не рассчиталась;
    -- насколько критична модель;

  - какие витрины и отчёты могут быть затронуты;
  - успели ли другие модели успешно завершиться;
  - была ли запущена выгрузка в ClickHouse;
    -- требуется ли немедленное вмешательство;

  - кого нужно уведомлять;
  - можно- какой селектор использовать для перезапуска.

  Ссылка на полный лог не заменяет диагностическое сообщение: оператор сначала должен открыть лог и самостоятельно искать первопричину среди вывода всей dbt-команды.

  ### Требование

  После выполнения dbt необходимо разбирать структурированный результат запуска, а не отправлять только ошибку BashOperator.

  Для каждой упавшей модели уведомление должно содержать:

  Среда: PROD
  Статус: ERROR
  Критичность: CRITICAL

  DAG: KAIZEN_LOADER_dbt
  Airflow task: dbt_task
  dbt-модель: dm_s_kaizen_personnel_involvement
  Физический объект: dm.kaizen_personnel_involvement
  Сущность: KAIZEN_LOADER

  Ошибка dbt: Database Error — column personnel_id does not exist
  Этап: run
  Начало: 03:30
  Длительностьность: 00:04:17

  Затронуты:
  - ClickHouse: dm_ka_personnel_meta
  - downstream-модели: 4
  - критичные потребители: отчёт «Вовлечённость персонала»

  Release ID: release-2026-09-11
  YouTrack: DWH-12345
  Commit SHA: abc123
  Invocation ID: ...

  Рекомендуемое действие:
  перезапустить модель и зависимые объекты после устранения ошибки.

  Airflow log: ссылка
  dbt log/artifact: ссылка
  Runbook: ссылка

  ### Откуда брать сведения

  - модель и текст ошибки — run_results.json;
  - граф зависимостей — manifest.json;
  - физическую таблицу — database, schema, alias из dbt metadata;
  - сущность — из тега или metadata модели;
  - ClickHouse DAG — из объектной ClickHouse-конфигурации;
  - release_id, YouTrack и commit SHA — из релизного контекста;
  - критичность и владелец — из metadata конкретной модели.

  Например:

  models:
    - name: dm_s_kaizen_personnel_involvement
      config:
        meta:
          entity: KAIZEN_LOADER
          criticality: critical
          owner: kaizen_team
          support_group: dwh_support
          sla_minutes: 60
          consumers:
            - kaizen_personnel_report
          runbook_url: https://...

  ### Уровни критичности

  Нужно формально определить хотя бы три уровня:

   Уровень     Значение                                                          Реакция                                                                               
  ━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   critical    Останавливает критичный процесс или отчётность                    Немедленный алерт дежурной команде
  ──────────  ────────────────────────────────────────────────────────────────  ────────────────────────────────────────
   high        Затрагивает важную витрину, но допустима ограниченная задержка    Алерт владельцу и поддержке
  ──────────  ────────────────────────────────────────────────────────────────  ────────────────────────────────────────
   normal      Некритичная модель или внутренний расчёт                          Обычное уведомление
  ──────────  ────────────────────────────────────────────────────────────────  ────────────────────────────────────────
   warning     Упавший тест или некритичное отклонение                           Предупреждение без аварийной эскалации

  Критичность лучше хранить на модели, а не определять вручную в коде callback.

  ### Задачи реализации

  1. Добавить metadata критичности, владельца, SLA и потребителей модели.
  2. Сохранять manifest.json и run_results.json после каждого запуска.
  3. Определять список упавших моделей и тестов.
  4. Извлекать содержательную dbt/database error вместо общей ошибки Bash.
  5. Определять затронутые downstream-модели и ClickHouse-выгрузки.
  6. Передавать в callback execution_guid, invocation_id, release ID и commit SHA.
  7. Формировать отдельное сообщение для каждой критичной ошибки либо одно структурированное сообщение со списком ошибок.
  8. Добавить ссылки на Airflow log и инструкцию восстановления.
  9. Разделить каналы уведомлений по критичности.
  10. Проверить формат сообщений на намеренно упавших моделях.

  ### Готово, когда

  При намеренном падении двух моделей разной критичности:

  - уведомление содержит имена обеих моделей;
  - указаны физические таблицы и сущность;
  - показана настоящая причина ошибки, а не только exit code 1;
  - указана критичность каждой модели;
  - перечислены затронутые ClickHouse- и downstream-объекты;
  - присутствуют release ID, YouTrack, commit SHA и invocation ID;
  - критичная ошибка направляется в аварийный канал;
  - некритичная ошибка не создаёт ложную критическую тревогу;
  - по сообщению понятно, что сломалось и куда перейти для восстановления.

  В самой Story 3 можно дополнить общее требование одним пунктом:

  > Наблюдаемость должна включать объектный алертинг. Уведомление обязано содержать упавшую dbt-модель, физический объект, причину ошибки, критичность, владельца,     
  > затронутые зависимости, релизный контекст и ссылку на инструкцию восстановления. Общего сообщения Bash command failed недостаточно.
