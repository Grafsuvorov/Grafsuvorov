Что я бы проверил прямо сейчас
1. Настоящие ли это дубли в STG
select
    "AUFNR",
    "VORNR",
    dt_insert,
    record_id,
    uuid,
    count(*) as cnt
from stg."RAL_IS2_TORO2_ORD_HDR_OPR"
group by 1,2,3,4,5
having count(*) > 1
order by cnt desc
limit 100;

Если здесь есть cnt > 1, то один и тот же распарсенный объект вставляется повторно.

2. Сколько версий приходится на заказ
select
    "AUFNR",
    count(distinct dt_insert) as versions_cnt,
    count(*) as rows_cnt,
    count(distinct "VORNR") as operation_cnt
from stg."RAL_IS2_TORO2_ORD_HDR_OPR"
group by 1
order by versions_cnt desc
limit 100;

Если, например:

versions_cnt = 50
operation_cnt = 10
rows_cnt ≈ 500

то это именно 50 полных снимков одного заказа.

3. Сколько строк реально остаётся после отбора последней версии
with last_dt as (
    select
        "AUFNR",
        max(dt_insert) as max_dt_insert
    from stg."RAL_IS2_TORO2_ORD_HDR_OPR"
    group by 1
)
select count(*)
from stg."RAL_IS2_TORO2_ORD_HDR_OPR" t
join last_dt ld
  on t."AUFNR" = ld."AUFNR"
 and t.dt_insert = ld.max_dt_insert;

Сравни с:

select count(*)
from stg."RAL_IS2_TORO2_ORD_HDR_OPR";

Если в STG 500 млн, а после отбора 80 млн, значит сотни миллионов строк парсятся и хранятся зря.

4. Есть ли дубли уже в ODS
select
    aufnr,
    vornr,
    count(*) as cnt
from ods.ral_is2_toro2_ord_opr
group by 1,2
having count(*) > 1
order by cnt desc
limit 100;

Если вернулся результат, то AUFNR + VORNR либо не является ключом, либо ODS не очищается/загружается некорректно.

Как это логичнее было бы сделать

Если каждое сообщение — полный снимок заказа, оптимальнее сначала определить последнее XML-сообщение для каждого заказа, а уже потом полностью разбирать операции.

Но здесь сложность: AUFNR находится внутри XML. Поэтому минимально разумная схема такая:

1. Лёгким проходом распарсить только Item и AUFNR
2. Для каждого AUFNR выбрать последний dt_insert
3. Только выбранные xml_item развернуть по ORDER_OPR
4. Загрузить актуальный набор операций

Сейчас же сделано наоборот:

1. Полностью разобрать все версии и все операции
2. Записать их в STG
3. В ODS выбрать последние

То есть тяжёлая часть выполняется до фильтрации.

Итог

Ты прав в главном: очень много данных парсится впустую, потому что актуальность применяется слишком поздно.

Но утверждение «парсятся только заголовки» неверно: операции ORDER_OPR тоже разворачиваются и парсятся. Просто поля заголовка копируются в каждую операцию, из-за чего визуально таблица выглядит как множество повторяющихся заголовков.

Главный архитектурный вопрос аналитикам должен звучать так:

Почему полная детализация всех операций выполняется по всем версиям XML за 30 дней, если в ODS затем используется только последняя версия каждого заказа? Нельзя ли выбрать актуальный Item/AUFNR до разворачивания ORDER_OPR?

И второй:

Гарантировано ли, что каждое сообщение содержит полный снимок всех операций заказа? Иначе выбор последнего dt_insert по AUFNR может привести к потере операций.
