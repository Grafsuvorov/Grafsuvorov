# Описание YAML-конфигурации объекта загрузки на примере `dm.sb_wuc`

## 1. Назначение YAML-файла

YAML-файл описывает объект хранилища данных и используется процессом загрузки для понимания:

* какую таблицу нужно загружать;
* к какой сущности и слою она относится;
* каким SQL-скриптом пересоздавать, очищать и наполнять таблицу;
* от каких таблиц зависит расчёт;
* какие проверки качества данных нужно выполнить после загрузки;
* по каким ключам проверять дубли;
* в каком порядке объект должен загружаться внутри сущности.

Пример объекта:

```yaml
table_name: sb_wuc
table_schema: dm
table_id: 1334
source_id: 15
source_type: GREENPLUM
flag_has_views: true
table_load_mode: TRUNCATE_INIT
job_id: 1
job_name: DM_SB_WUC
table_loading_index: 1
entity_id: 35
entity_name: BI_SB_WUC
object_type: TABLE
```

Данный YAML описывает таблицу:

```text
dm.sb_wuc
```

Она относится к сущности:

```text
BI_SB_WUC
```

и загружается в Greenplum.

---

## 2. Основные поля объекта

### `table_name`

Имя таблицы без схемы.

Пример:

```yaml
table_name: sb_wuc
```

Означает, что загружаемый объект называется `sb_wuc`.

---

### `table_schema`

Схема, в которой находится таблица.

Пример:

```yaml
table_schema: dm
```

Полное имя объекта:

```text
dm.sb_wuc
```

---

### `table_id`

Уникальный идентификатор таблицы в рамках метаданных загрузки.

Пример:

```yaml
table_id: 1334
```

Используется для идентификации объекта в технических таблицах, логах загрузки и при построении порядка выполнения.

Важно: `table_id` также может влиять на порядок загрузки внутри сущности, особенно для слоёв `dm_calc`, `dm`, `dm_view`. Если одна таблица зависит от другой в рамках одной сущности, у зависимой таблицы должен быть `table_id` больше, чем у таблицы-источника.

---

### `source_id`

Идентификатор источника данных.

Пример:

```yaml
source_id: 15
```

Используется для связи объекта с конкретным источником в технических метаданных.

---

### `source_type`

Тип источника/платформы, где находится объект.

Пример:

```yaml
source_type: GREENPLUM
```

Означает, что объект загружается в Greenplum.

---

### `flag_has_views`

Флаг наличия зависимых представлений.

Пример:

```yaml
flag_has_views: true
```

Если `true`, значит от таблицы могут зависеть view. Это важно при релизе, пересоздании таблицы и анализе зависимостей.

При изменении структуры таблицы необходимо учитывать зависимые представления, чтобы не сломать downstream-объекты.

---

### `table_load_mode`

Режим загрузки таблицы.

Пример:

```yaml
table_load_mode: TRUNCATE_INIT
```

Означает, что таблица загружается через очистку и полную вставку данных.

Типовой сценарий:

```sql
truncate table dm.sb_wuc;

insert into dm.sb_wuc (...)
select ...
```

Важно: при таком режиме нужно учитывать, что таблица на время загрузки может быть очищена. Поэтому необходимо контролировать порядок запуска зависимых объектов и не допускать параллельного чтения/пересчёта, если это может привести к неконсистентным данным.

---

### `job_id`

Идентификатор задания загрузки.

Пример:

```yaml
job_id: 1
```

Используется в технических метаданных и логах.

---

### `job_name`

Название задания загрузки.

Пример:

```yaml
job_name: DM_SB_WUC
```

Используется в логах загрузки и технических полях таблицы, например в поле `job_name`.

---

### `table_loading_index`

Индекс загрузки таблицы.

Пример:

```yaml
table_loading_index: 1
```

Может использоваться для дополнительного управления порядком загрузки объектов внутри процесса.

---

### `entity_id`

Идентификатор сущности.

Пример:

```yaml
entity_id: 35
```

Сущность объединяет набор таблиц, которые относятся к одному бизнес-направлению или витрине.

---

### `entity_name`

Наименование сущности.

Пример:

```yaml
entity_name: BI_SB_WUC
```

В данном примере таблица `dm.sb_wuc` относится к сущности `BI_SB_WUC`.

---

### `object_type`

Тип объекта.

Пример:

```yaml
object_type: TABLE
```

Возможные значения могут быть:

```text
TABLE
VIEW
TECHNICAL_TABLE
DQ_CHECK
BACKUP
```

В данном случае объект является физической таблицей.

---

## 3. Интервал загрузки

Блок:

```yaml
table_load_interval:
    days: 1
    hours: 0
    minutes: 0
    seconds: 0
```

Описывает периодичность загрузки объекта.

В данном примере таблица должна загружаться один раз в сутки.

---

## 4. Управление запуском

### `flag_waiting_dag_finished`

Пример:

```yaml
flag_waiting_dag_finished: false
```

Флаг ожидания завершения другого DAG/процесса.

Если `true`, загрузка может ожидать завершения внешнего процесса.
Если `false`, объект запускается без такого ожидания.

---

### `start_date`

Дата и время старта загрузки.

Пример:

```yaml
start_date: '2024-12-22 00:30:00'
```

Используется планировщиком для определения момента, с которого объект может участвовать в расписании загрузки.

---

## 5. SQL-скрипты объекта

### `sql_query_recreate_init`

Путь к скрипту пересоздания таблицы.

Пример:

```yaml
sql_query_recreate_init: meta_info/database/greenplum/schema_name/tech_etl/etl_loads_entity/BI_SB_WUC/dm/sb_wuc/sql_query_recreate_init.sql
```

В этом файле обычно находится DDL таблицы:

```sql
create table ...
```

или логика пересоздания объекта.

---

### `sql_query_insert_init`

Путь к основному скрипту вставки данных.

Пример:

```yaml
sql_query_insert_init: meta_info/database/greenplum/schema_name/tech_etl/etl_loads_entity/BI_SB_WUC/dm/sb_wuc/sql_query_insert_init.sql
```

В этом файле находится основной расчёт таблицы:

```sql
insert into dm.sb_wuc (...)
select ...
```

---

### `sql_query_truncate`

Путь к скрипту очистки таблицы.

Пример:

```yaml
sql_query_truncate: meta_info/database/greenplum/schema_name/tech_etl/etl_loads_entity/BI_SB_WUC/dm/sb_wuc/sql_query_truncate.sql
```

Обычно содержит:

```sql
truncate table dm.sb_wuc;
```

Если в блоке truncate используется не `truncate`, а специальная логика, это должно быть явно описано в скрипте.

---

## 6. Блок `depends_on`

Блок `depends_on` содержит список всех таблиц, на основе которых строится текущий объект.

Пример:

```yaml
depends_on:
    dds:
        - sales_bundle_and_delivery_relationship
    dict_dds:
        - business_location
        - business_location_texts
    dm_calc:
        - finish_goods_warehouse_stock_plant_by_date
        - sales_bundle_transport_hub_turnover_sdt0004
    ods:
        - hypdb_v_hfm_pcs013_1_014_1_al
```

Для таблицы `dm.sb_wuc` это означает, что при расчёте используются источники из слоёв:

```text
dds
dict_dds
dm_calc
ods
```

### Для чего нужен `depends_on`

`depends_on` используется для:

1. Построения графа зависимостей.
2. Определения порядка загрузки таблиц.
3. Анализа влияния изменений.
4. Понимания, какие объекты могут повлиять на результат таблицы.
5. Отображения lineage в инструменте мониторинга зависимостей.
6. Проверки, что все необходимые источники были загружены до запуска целевой таблицы.

Если объект указан в `depends_on`, это означает, что текущая таблица не должна загружаться раньше, чем будут готовы её источники.

### Важное правило

Если таблица `dm.sb_wuc` использует в SQL таблицу-источник, она должна быть указана в `depends_on`.

Если источник не указан, возможны проблемы:

* неверный порядок загрузки;
* запуск таблицы до готовности данных;
* неполный lineage;
* некорректный анализ влияния при изменении источника;
* ошибки в мониторинге зависимостей.

---

## 7. Блок `verification`

Блок `verification` описывает проверки качества данных, которые должны выполняться после загрузки таблицы.

Пример:

```yaml
verification:
    - duplicate_check
    -   business:
            - dq_sd0001
            - dq_sd0002
            - dq_sd0003
```

### `duplicate_check`

Стандартная техническая проверка на дубли.

Она использует ключевые поля из блока `key_attributes`.

Для данного объекта ключ:

```yaml
key_attributes:
    - delivery_number_sales
    - batch
    - dt_report
```

Проверка ищет ситуации, когда в таблице есть несколько строк с одинаковым набором ключевых атрибутов.

Пример логики:

```sql
select
    delivery_number_sales,
    batch,
    dt_report,
    count(*) as row_cnt
from dm.sb_wuc
group by
    delivery_number_sales,
    batch,
    dt_report
having count(*) > 1;
```

Если такие строки найдены, значит в таблице есть дубли по бизнес-ключу.

---

### `business`

Блок бизнес-проверок.

Пример:

```yaml
business:
    - dq_sd0001
    - dq_sd0002
    - dq_sd0003
```

Это список специальных DQ-проверок, которые относятся к конкретной бизнес-логике витрины.

Такие проверки могут контролировать:

* корректность расчётных показателей;
* допустимые отклонения;
* наличие обязательных значений;
* согласованность с другими витринами;
* бизнес-правила;
* качество данных после релиза.

Результаты бизнес-проверок сохраняются в отдельные DQ-таблицы или общую таблицу результатов проверок, в зависимости от принятой реализации.

Например, для проверок с кодами `dq_sd0001`, `dq_sd0002`, `dq_sd0003` результат может сохраняться в таблицы вида:

```text
dm.dq_sd0001
dm.dq_sd0002
dm.dq_sd0003
```

или в общую таблицу результатов DQ, если для проекта используется единое хранилище проверок.

Каждая бизнес-проверка должна иметь описание:

* что проверяется;
* по какой таблице;
* какой порог считается ошибкой;
* куда сохраняется результат;
* какой инцидент создаётся при нарушении;
* кто ответственный за разбор.

---

## 8. Блок `key_attributes`

Блок `key_attributes` содержит список ключевых атрибутов таблицы.

Пример:

```yaml
key_attributes:
    - delivery_number_sales
    - batch
    - dt_report
```

Для таблицы `dm.sb_wuc` ключом считаются:

```text
delivery_number_sales
batch
dt_report
```

### Для чего нужны ключевые атрибуты

Они используются для проверки дублей.

Если в таблице есть две или более строки с одинаковыми значениями по этим полям, это считается дублем.

Пример:

| delivery_number_sales | batch | dt_report  | Количество строк |
| --------------------- | ----- | ---------- | ---------------- |
| 123456                | B001  | 2026-06-01 | 2                |

Такая ситуация должна попадать в результат `duplicate_check`.

### Важное правило

`key_attributes` должны отражать реальный бизнес-ключ таблицы.

Если указать слишком мало полей, проверка будет находить ложные дубли.
Если указать слишком много полей, проверка может не найти реальные дубли.

---

## 9. Как YAML используется в процессе загрузки

Общий процесс:

1. Система читает YAML-файл объекта.
2. Определяет схему и имя таблицы.
3. Определяет режим загрузки.
4. Определяет SQL-скрипты для recreate, truncate и insert.
5. Проверяет зависимости из `depends_on`.
6. Определяет порядок запуска относительно других объектов.
7. Запускает очистку и вставку данных.
8. Выполняет технические и бизнес-проверки из `verification`.
9. Использует `key_attributes` для проверки дублей.
10. Записывает результат загрузки и проверок в технические таблицы мониторинга.

---

## 10. Что важно проверять при изменении YAML

При изменении YAML-файла необходимо проверить:

1. Правильно ли указаны `table_schema` и `table_name`.
2. Не пересекается ли `table_id` с другим объектом.
3. Корректно ли указан `entity_id` и `entity_name`.
4. Правильно ли выбран `table_load_mode`.
5. Существуют ли все SQL-файлы по указанным путям.
6. Все ли источники из SQL указаны в `depends_on`.
7. Нет ли лишних зависимостей, которые не используются в SQL.
8. Корректно ли указаны `key_attributes`.
9. Есть ли в таблице все поля из `key_attributes`.
10. Правильно ли указаны бизнес-проверки.
11. Понятно ли, куда сохраняются результаты DQ-проверок.
12. Не нарушается ли порядок загрузки внутри сущности.

---

## 11. Пример краткого описания для `dm.sb_wuc`

Таблица `dm.sb_wuc` является объектом слоя `dm` в сущности `BI_SB_WUC`.

Загрузка выполняется в Greenplum в режиме `TRUNCATE_INIT`, то есть таблица очищается и наполняется заново.

Расчёт строится на источниках из слоёв `dds`, `dict_dds`, `dm_calc` и `ods`, которые указаны в блоке `depends_on`.

После загрузки выполняются проверки:

* `duplicate_check` — проверка дублей по ключу `delivery_number_sales`, `batch`, `dt_report`;
* `dq_sd0001`, `dq_sd0002`, `dq_sd0003` — бизнес-проверки качества данных.

Ключевые атрибуты таблицы:

```text
delivery_number_sales
batch
dt_report
```

Они используются для контроля уникальности строк в таблице.

---

## 12. Итог

YAML-файл является техническим паспортом объекта загрузки.

Он нужен не только для запуска SQL-скрипта, но и для:

* управления порядком загрузки;
* построения lineage;
* контроля зависимостей;
* запуска DQ-проверок;
* проверки дублей;
* мониторинга качества данных;
* анализа влияния изменений;
* сопровождения объекта после релиза.

Корректное заполнение YAML напрямую влияет на стабильность загрузки, качество данных и удобство сопровождения витрины.
