Если dt_insert одинаковый → она пропустит записи
Как работает её фильтр
Она выбирает из stg только строки:
где dt_insert > max(dt_insert) в ods
Обрати внимание: строго >.
Пример
В ODS сейчас:
rw_part	dt_insert
A	2026-02-20 19:10
max(dt_insert) = 2026-02-20 19:10
В stg пришёл новый инкремент:
rw_part	dt_insert
B	2026-02-20 19:10
C	2026-02-20 19:10
НО dt_insert одинаковый.
Фильтр:
dt_insert > '2026-02-20 19:10'
Ни одна строка не пройдёт.
👉 B и C никогда не попадут в ODS.
Почему это возможно?
Если dt_insert:
ставится с округлением до минуты
проставляется batch-ом
несколько пакетов пришли в одну секунду
2️⃣ Если повторный запуск → может удалить лишнее
Её delete:
delete from ods
where rw_part in (
   select rw_part из stg где dt_insert > max(dt_insert)
)
Сценарий
1️⃣ Запуск прошёл
2️⃣ delete удалил старые rw_part
3️⃣ insert вставил новые
4️⃣ Но процесс упал ДО COMMIT (или не полностью вставил)
Теперь:
часть данных удалена
часть не вставлена
При повторном запуске:
max(dt_insert) уже увеличился
Фильтр может не выбрать нужные строки
И ODS останется без части данных.
👉 Потеря данных.
3️⃣ Если dt_insert не монотонный → будут пропуски
Что значит "не монотонный"?
Монотонный = всегда растёт.
Например:
19:10
20:10
22:10
00:10
Что если источник отправил старый пакет позже?
Пример:
ODS max(dt_insert) = 2026-02-20 22:10
Позже приходит запись с:
dt_insert = 2026-02-20 20:10
Она логически новая (переслали повторно),
но фильтр:
20:10 > 22:10 → false
Она никогда не попадёт в ODS.
4️⃣ Почему это особенно опасно в PROD
Если источник:
перезапускается
переотправляет данные
задерживает пакет
меняет время на стороне SAP/XI
Ты теряешь записи навсегда.
5️⃣ Самая тонкая проблема — batch внутри одного dt_insert
Она внутри делает:
row_number() over (partition by RW_PART order by dt_insert desc)
Но если:
rw_part = A
dt_insert = 19:10
Пришло 2 строки с одинаковым dt_insert —
какая из них будет rn = 1?
👉 Непредсказуемо.
Postgres не гарантирует порядок при равенстве.
6️⃣ Почему это работает на DEV, но может убить PROD
На DEV:
маленький объём
тестовые данные
стабильный поток
На PROD:
задержки
переотправки
разные зоны времени
race conditions
7️⃣ Итог по каждому пункту
🔴 Одинаковый dt_insert
→ новые записи могут не попасть в ODS
🔴 Повторный запуск
→ возможно частичное удаление без вставки
🔴 Не монотонный dt_insert
→ потеря данных
