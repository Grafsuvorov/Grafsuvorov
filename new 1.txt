## Задача: пострелизный контроль качества изменённых витрин слоя DM

  ### Цель

  После каждого релиза автоматически проверять все изменённые физические витрины слоя dm, фиксировать результаты проверок в отдельной таблице и использовать единый
  механизм для дальнейшего добавления бизнес-проверок.

  Проверки должны запускаться на PROD после завершения расчёта объектов и не зависеть от того, выполнялись они через legacy ETL или dbt.

  ### Объекты проверки

  В первый этап включаются только физические таблицы схемы:

  dm.*

  Не включаются:

  - dm_view;
  - ClickHouse-объекты;
  - неизменённые витрины;
  - технические таблицы.

  Список объектов должен определяться не вручную, а из текущего релиза:

  - release_id;
  - tech_etl.release_log;
  - tech_etl.release_objects либо фактической таблицы с объектами релиза;
  - commit SHA и списка изменённых объектов.

  ### Последовательность выполнения

  1. Релизный DAG получает release_id.
  2. В рамках релиза фиксируются все изменённые физические объекты.
  3. Релиз выполняет расчёт и загрузку витрин.
  4. После успешного завершения релиза запускается пострелизный DQ DAG.
  5. DQ DAG выбирает только изменённые таблицы схемы dm.
  6. Для каждой таблицы определяются:
      - бизнес-ключ;
      - фильтр проверки;
      - тип SCD;
      - набор активных проверок;
      - порог критичности.

  7. Проверки запускаются параллельно с ограничением по пулу.
  8. Результат каждой проверки записывается в таблицу результатов.
  9. По критическим ошибкам отправляется уведомление в Pulse.
  10. В результатах сохраняются ссылка на релиз, объект, задачу YouTrack, commit SHA и запуск DAG.

  ## Минимальная проверка на дубли

  Для каждой изменённой DM-витрины выполняется проверка по бизнес-ключу:

  select
      count(*) as duplicate_group_count,
      coalesce(sum(row_count - 1), 0) as duplicate_row_count
  from (
      select
          key_column_1,
          key_column_2,
          count(*) as row_count
      from dm.target_table
      where <filter>
      group by
          key_column_1,
          key_column_2
      having count(*) > 1
  ) duplicates;

  Необходимо сохранять отдельно:

  - количество строк в таблице;
  - количество групп-дублей;
  - количество лишних строк;
  - максимальный размер группы дублей.

  Если ключ состоит из нескольких колонок, группировка выполняется по полному ключу.

  Для SCD2 в ключ должны входить необходимые поля версии, если это предусмотрено методикой проверки.

  ## Таблица результатов

  Предлагаемое имя:

  tech_etl.release_data_quality_result

  Основные поля:

  result_id
  release_id
  invocation_id
  task_id
  commit_sha

  schema_name
  table_name
  entity_name
  object_type

  check_code
  check_type
  check_name
  check_version

  business_key
  check_filter
  check_parameters

  started_at
  finished_at
  duration_sec

  status
  severity

  row_count
  duplicate_group_count
  duplicate_row_count
  max_duplicate_group_size

  metric_value
  metric_json

  error_message
  airflow_dag_id
  airflow_run_id
  created_at

  ### Значения status

  PASSED
  FAILED
  ERROR
  SKIPPED

  ### Значения severity

  INFO
  WARNING
  CRITICAL

  metric_json нужен для будущих проверок, которые возвращают больше одного показателя.

  Например:

  {
    "null_count": 12,
    "invalid_count": 4,
    "threshold": 0
  }

  ## Расширение для бизнес-проверок

  Чтобы не ограничиваться дублями, необходимо ввести единый идентификатор проверки:

  check_code
  check_type

  Примеры:

  DM_DUPLICATES
  DM_NULLS
  DM_REFERENTIAL_INTEGRITY
  DM_BUSINESS_RULE
  DM_FRESHNESS
  DM_ROW_COUNT_CHANGE

  Для бизнес-проверки результатом должен быть не только статус, но и измеряемый показатель:

  check_code: DM_BUSINESS_0001
  check_type: business
  check_name: Отсутствие проводок без договора
  severity: CRITICAL
  metric_value: 245
  threshold: 0

  SQL самой проверки должен храниться в Git-репозитории и проходить ревью. В таблице результатов нужно хранить ссылку на файл или версию проверки, а не только текст
  запроса.

  Например:

  check_path:
  dbt_greenplum_elt/models/dq/business/dm_account_debt_contract.sql

  check_commit_sha:
  abc123...

  ## Повторный запуск

  Повторная проверка не должна затирать предыдущий результат.

  Каждый запуск обязан иметь собственный:

  invocation_id
  airflow_run_id
  started_at

  Это позволит сравнивать результаты до и после исправления.

  Для защиты от дублей результатов рекомендуется уникальность:

  (release_id, table_name, check_code, invocation_id)

  ## Обработка ошибок

  Если для изменённой DM-витрины не найден бизнес-ключ или конфигурация проверки:

  - результат записывается со статусом SKIPPED или ERROR;
  - причина сохраняется в error_message;
  - в Pulse отправляется понятное уведомление;
  - объект не должен исчезать из списка проверок молча.

  Для критической проверки:

  - создаётся инцидент;
  - в уведомлении указываются схема, таблица, тип проверки и фактический результат;
  - добавляется ссылка на Airflow task и релизную задачу YouTrack.

  ## Требования к интеграции с текущим релизом

  В результатах должны сохраняться:

  - release_id;
  - номер задачи YouTrack;
  - commit SHA;
  - физический объект;
  - dbt-модель, если объект рассчитывается через dbt;
  - Airflow DAG и конкретный run_id;
  - дата и время проверки;
  - итог проверки;
  - информация о повторном запуске.

  Таким образом, можно построить полную цепочку:

  YouTrack-задача
      ↓
  release_id
      ↓
  изменённая DM-витрина
      ↓
  DQ-проверка
      ↓
  результат
      ↓
  инцидент или подтверждение успешного релиза

  ## Критерии приёмки

  Задача считается выполненной, если:

  1. После релиза автоматически находятся все изменённые физические таблицы dm.
  2. Для каждой таблицы запускается проверка на дубли.
  3. Результат записывается в tech_etl.release_data_quality_result.
  4. В результате есть release_id, таблица, ключ, фильтр, статус и метрики.
  5. Ошибка одной проверки не скрывает результаты остальных.
  6. Повторный запуск создаёт новую запись, не затирая предыдущую.
  7. В Pulse отображаются конкретные схема, таблица и тип проверки.
  8. Проверка не запускается для dm_view.
  9. Таблица результатов поддерживает будущие бизнес-проверки без изменения структуры.
  10. Отсутствие конфигурации ключа не приводит к молчаливому пропуску.
  11. Для dbt и legacy ETL используется единый формат результата.
  12. Результат можно связать с YouTrack-задачей и релизом.

  ### Рекомендуемая декомпозиция

  Основную задачу лучше оформить как Epic, а внутри создать задачи:

  1. Спроектировать таблицу результатов.
  2. Определить источник изменённых объектов релиза.
  3. Реализовать DQ DAG.
  4. Реализовать проверку дублей.
  5. Добавить запись результатов и историю запусков.
  6. Добавить алертинг в Pulse.
  7. Добавить конфигурацию бизнес-проверок.
  8. Добавить интеграцию с dbt.
  9. Провести нагрузочное тестирование на крупных DM-таблицах.
  10. Подготовить эксплуатационный runbook.
