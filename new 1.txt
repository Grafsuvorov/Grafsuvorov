ТЗ
  Нужно встроить существующий скрипт в Git/CI/CD так, чтобы он автоматически запускался при merge request / merge в рабочую ветку и валидировал изменения по ветке.

  Цель
  Автоматизировать проверку ветки перед вливанием, чтобы:

  - не запускать валидацию вручную из интерфейса
  - получать результат проверки прямо в pipeline
  - блокировать merge при критических ошибках
  - сохранять понятный отчёт по каждому проверенному объекту

  Что уже есть
  Есть существующий локальный скрипт валидации ветки, который:

  - принимает ветку или набор объектов
  - проходит по объектам ветки
  - валидирует их по текущим правилам
  - возвращает результаты по каждому объекту

  Задача разработчика:

  - не переписывать бизнес-логику проверки с нуля
  - адаптировать текущий скрипт под запуск в CI/CD
  - сделать его стабильным для non-interactive окружения

  Что должно получиться
  После внедрения:

  - при создании или обновлении merge request запускается pipeline job
  - job определяет изменённые объекты в ветке
  - по каждому объекту запускается существующая валидация
  - в конце формируется итоговый статус:
      - success, если ошибок нет
      - failed, если есть критические ошибки
      - warning допустим опционально, если есть некритичные замечания
  - merge должен блокироваться при failed

  Требования к интеграции

  1. Скрипт должен запускаться из CLI.
     Примерно в формате:

     validate_branch --branch <branch_name>
     или

     ./validate_branch.sh <branch_name>
     ./validate_branch.sh <branch_name>
  2. Скрипт должен уметь работать без UI и без ручного ввода.
  3. Скрипт должен возвращать корректный exit code:

  - 0 — валидация успешна
  - 1 — есть ошибки валидации
  - 2 и выше — техническая ошибка запуска

  4. Скрипт должен писать лог в stdout/stderr так, чтобы он был читаем в pipeline.
  5. По возможности нужен машинно-читаемый артефакт:

  - json
  - или junit xml
  - или csv

  Рекомендуемый формат:

  {
    "branch": "feature/xxx",
    "checked_objects": 6,
    "success_count": 4,
    "warning_count": 1,
    "error_count": 1,
    "items": [
      {
        "object": "schema.table_name",
        "status": "success",
        "message": "validated"
      },
      {
        "object": "schema.bad_table",
        "status": "error",
        "message": "missing required field"
      }
    ]
  }

  Что именно должен сделать разработчик

  1. Взять существующий скрипт валидации ветки.
  2. Выделить из него CI-friendly entrypoint.
  3. Убрать зависимости от:

  - локального UI
  - интерактивных prompt
  - ручного выбора объектов

  4. Добавить определение списка изменённых объектов по ветке.
  5. Подключить запуск в CI/CD pipeline.
  6. Настроить fail pipeline при критических ошибках.
  7. Сохранить артефакты проверки.
  8. Добавить краткую документацию:

  - как запускается локально
  - как запускается в pipeline
  - какие переменные окружения нужны
  - какие exit codes используются

  Логика проверки
  Нужно сохранить текущую бизнес-логику валидации без изменений, если она уже корректна.
  Если в текущем скрипте есть разделение на типы ошибок, нужно сохранить категории:

  - ошибка
  - warning
  - success

  Если сейчас категорий нет, минимум нужен такой уровень:

  - критическая ошибка, блокирующая merge
  - информационное сообщение

  Источник объектов для проверки
  Разработчику нужно реализовать один из вариантов:

  - брать список изменённых файлов из git diff относительно target branch
  - по ним определять связанные объекты
  - валидировать только их

  Минимально ожидаемое поведение:

  - валидируются только объекты, затронутые в текущей ветке
  - не валидируется весь репозиторий целиком без необходимости

  Интеграция в CI/CD
  Нужно встроить в текущий pipeline как отдельный stage/job, например:

  - validate_branch
  - branch_checks

  Запуск:

  - на merge request
  - при push в ветку MR
  - опционально на merge в main/develop как safety check

  Ожидаемое поведение pipeline:

  - если есть ошибка валидации, job красный
  - если ошибок нет, job зелёный
  - в логах видно, какой объект упал и почему

  Требования к логированию
  В логах должно быть видно:

  - какая ветка проверяется
  - сколько объектов найдено
  - какой объект проверяется сейчас
  - результат по каждому объекту
  - финальная сводка

  Пример:

  Branch: feature/abc
  Found objects: 6

  [1/6] schema.table_1 -> OK
  [2/6] schema.table_2 -> OK
  [3/6] schema.table_3 -> ERROR: invalid config
  ...

  Summary:
  OK: 4
  WARN: 1
  ERROR: 1

  Требования к отказоустойчивости
  Если:

  - не удалось определить branch
  - не удалось определить список объектов
  - не хватает обязательных переменных окружения
  - недоступны нужные зависимости

  то job должен падать с понятной технической ошибкой.

  Что желательно дополнительно

  - возможность локального запуска тем же способом, что и в CI
  - возможность проверить один объект отдельно:

  validate_branch --object schema.table_name

  - публикация summary в merge request comment, если это поддерживается CI
  - junit report для красивого отображения в pipeline UI

  Критерии готовности
  Задача считается выполненной, если:

  1. Скрипт запускается в CI без ручных действий.
  2. Pipeline видит результат и корректно падает при ошибках.
  3. Валидация идёт только по изменённым объектам ветки.
  4. В логах и/или артефакте видно, какой объект не прошёл и почему.
  5. Есть короткая инструкция по использованию.

  Что передать разработчику вместе с ТЗ
  Нужно приложить:

  - сам текущий скрипт
  - пример входных данных
  - пример успешного результата
  - пример результата с ошибкой
  - список обязательных переменных окружения
  - описание, как сейчас определяется список объектов в ветке, если это уже реализовано
