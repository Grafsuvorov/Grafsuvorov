# ТЗ: уведомления о релизных слотах из YouTrack в канал Pulse

## 1. Цель

Реализовать автоматическую отправку уведомлений в канал Pulse по релизным слотам из YouTrack.

Система должна:

* по понедельникам отправлять расписание релизов на текущую неделю;
* ежедневно проверять изменения дат релизов;
* при изменении даты релиза отправлять уведомление о переносе.

## 2. Источник данных

Источник: YouTrack.

Необходимо получать задачи с типом карточки:

`Release Slot`

Основные поля карточки:

* ID задачи;
* название задачи, например `Релиз FI`, `Релиз SD`, `Релиз MANAGEMENT_REPORTING`;
* направление релиза, можно определять из названия или отдельного поля, если оно есть;
* исполнитель;
* плановая/фактическая дата релиза;
* статус задачи;
* ссылка на задачу.

## 3. DAG 1: недельное расписание релизов

Название DAG:

`yt_release_weekly_schedule`

Расписание запуска:

Каждый понедельник утром, например в 09:00.

Логика:

1. Подключиться к YouTrack API.
2. Получить все карточки типа `Release Slot`, у которых дата релиза попадает в текущую календарную неделю: понедельник–воскресенье.
3. Сгруппировать релизы по дате.
4. Сформировать сообщение для Pulse.
5. Отправить сообщение в релизный канал Pulse.

Пример сообщения:

🚀 Релизное расписание на неделю
Период: 24.06.2026 — 30.06.2026

📅 Среда, 26.06
• Релиз FI
Ответственный: Иванов И.И.
Дата релиза: 26.06.2026 18:00
Карточка: YT-12345

• Релиз SD
Ответственный: Петров П.П.
Дата релиза: 26.06.2026 20:00
Карточка: YT-12346

📅 Четверг, 27.06
• Релиз MANAGEMENT_REPORTING
Ответственный: Сидоров С.С.
Дата релиза: 27.06.2026 19:00
Карточка: YT-12347

## 4. DAG 2: ежедневная проверка изменений дат релиза

Название DAG:

`yt_release_date_change_monitoring`

Расписание запуска:

Каждый день, например в 09:00.

Логика:

1. Подключиться к YouTrack API.
2. Получить актуальный список карточек типа `Release Slot`.
3. Сравнить текущие значения с предыдущим сохраненным состоянием.
4. Если у карточки изменилась дата релиза, отправить уведомление в Pulse.
5. Обновить сохраненное состояние.

## 5. Хранение состояния

Необходимо создать служебную таблицу для хранения последнего известного состояния карточек.

Пример структуры:

```sql
create table release_slot_state (
    issue_id text primary key,
    issue_title text,
    release_direction text,
    assignee text,
    release_date timestamp,
    status text,
    issue_url text,
    hash_value text,
    updated_dttm timestamp default current_timestamp
);
```

`hash_value` рассчитывать по ключевым полям:

* release_date;
* assignee;
* status;
* issue_title.

Основной критерий отправки уведомления о переносе:

`release_date` изменилась относительно предыдущего сохраненного значения.

## 6. Уведомление о переносе релиза

Если дата релиза изменилась, отправлять сообщение:

🔄 Перенос релиза

Релиз: FI
Карточка: YT-12345
Ответственный: Иванов И.И.

Было: 26.06.2026 18:00
Стало: 28.06.2026 18:00

Ссылка на карточку: <ссылка>

## 7. Требования к обработке ошибок

Если YouTrack API недоступен:

* DAG должен завершиться с ошибкой;
* ошибка должна быть видна в логах Airflow.

Если Pulse API недоступен:

* сообщение не считается отправленным;
* DAG должен завершиться с ошибкой;
* при следующем запуске изменение не должно потеряться.

## 8. Переменные/конфигурация

Вынести в Airflow Variables или Connections:

* URL YouTrack;
* токен YouTrack;
* query для поиска карточек `Release Slot`;
* URL/API Pulse;
* ID канала Pulse;
* время запуска DAG;
* список направлений релизов при необходимости: FI, SD, LE, MM, MANAGEMENT_REPORTING.

## 9. Критерии приемки

Задача считается выполненной, если:

1. По понедельникам в Pulse приходит расписание релизов на текущую неделю.
2. В расписании отображаются дата, направление, исполнитель и ссылка на карточку.
3. При изменении даты релиза в YouTrack приходит отдельное уведомление о переносе.
4. Повторные уведомления по одному и тому же изменению не отправляются.
5. Состояние карточек сохраняется в служебной таблице.
6. Ошибки интеграции видны в логах Airflow.
