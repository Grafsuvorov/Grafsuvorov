Приоритизация задач и планирование релизов

В команде разработки и аналитики часто возникает проблема: все задачи считаются приоритетными. В итоге релизы перегружены, инженеры не успевают оптимизировать код, а пользователи сталкиваются с некорректными данными.

Чтобы исправить это, вводим единый подход к оценке и планированию задач.

1. Единый скоринг задач

Каждая задача оценивается по трём критериям:

Value (ценность)

5 — критично для бизнеса (финансовая отчётность, KPI, данные топ-менеджменту)

3 — важно для отдела, влияет на часть пользователей

1 — косметическая правка или nice-to-have

Risk (риск/неопределённость)

5 — новые сложные источники, много зависимостей, мало документации

3 — доработка существующих витрин

1 — простая корректировка колонок

⚠️ Чем выше риск, тем ниже итоговый приоритет.

Effort (затраты, “футболки”)

S = 0.5–1 день (1 поинт)

M = 2–3 дня (2 поинта)

L = 4–6 дней (3 поинта)

XL = >1 недели (5 поинтов)

2. Формула приоритета
Приоритет = Value × (1 / Risk) ÷ Effort


Пример

Задача А: Value=5, Risk=2, Effort=S (1) → Приоритет = 2.5

Задача B: Value=3, Risk=1, Effort=M (2) → Приоритет = 1.5
➡️ Задача А выше.

3. Capacity-план на релиз

Чтобы не перегружать релизы, вводится корзина задач:

Вместимость корзины на направление объявляет лид инженеров (например, 12 S-поинтов).

Складываем Effort всех задач → если превышает вместимость, лишние задачи переносятся в следующий релиз.

Пример

4 задачи S = 4 поинта

3 задачи M = 6 поинтов

1 задача L = 3 поинта
Итого = 13 поинтов → переносим одну задачу.

4. Срочные задачи

По умолчанию задача не срочная.

“Срочная” = отдельный класс с:

SLA (например, 24 часа)

обязательным пост-мортем (почему появилась вне плана, можно ли было предусмотреть).

5. Процесс на практике

Аналитик приносит задачу.

Вместе с инженером оценивают Value, Risk, Effort.

В backlog заносится задача с этими параметрами.

На планировании задачи сортируются по приоритету.

Лид инженеров “отрезает” корзину (например, 12 S-поинтов).

Остальные задачи переносятся в следующий релиз.

Срочные задачи идут отдельным треком.

Результат

Инженеры понимают реальный объём.

Аналитики видят прозрачные правила приоритизации.

Срочность перестаёт ломать процесс.

Релизы становятся предсказуемыми и управляемыми.


Шаблон скоринга задачи
Поле	Значение	Комментарий
Value (ценность)	1 / 3 / 5	5 — критично (KPI, финансы), 3 — важно для отдела, 1 — косметика
Risk (риск/неопределённость)	1 / 3 / 5	5 — новые источники/сильные зависимости, 3 — доработка витрин, 1 — простая правка
Effort (затраты, “футболка”)	S / M / L / XL	S = 0.5–1 дн., M = 2–3 дн., L = 4–6 дн., XL = >1 недели
Приоритет (авторасчёт)	Value × (1/Risk) ÷ Effort	Используется при сортировке задач
Срочность	Да / Нет	Срочные задачи идут отдельным треком с SLA
SLA (если срочная)	Часы/дни	Например: выполнить ≤ 24 часов
Пост-мортем (если срочная)	ссылка/описание	Обязательно заполняется после закрытия задачи
