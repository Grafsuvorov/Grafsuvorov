Проблемы и риски

Детали в «по-одной таблице на проверку». Через месяц будут десятки/сотни таблиц, сложнее сопровождать, мигрировать, настраивать права, писать запросы и алерты.

Нет формальной модели запуска/идемпотентности. Не описаны run_id, версия данных/партиции, как пересчитывать/перезапускать, как связывать с пайплайнами.

Нет порогов и политики алертинга. Не определены SLI/SLO/Severity/эскалации → дашборд есть, реакции нет.

Слабая аналитика качества. Нет “coverage”, доли проверенных строк/полей, динамики пер-категория DQ, срезов по системам/сущностям.

Раздувание схемы DM. Хранить логи в dm — спорно; DM — для бизнес-витрин. Логи DQ лучше держать в отдельной схеме (или в ClickHouse для «деталей»).

Нет формата спецификаций проверок. Скрипты есть, но не стандартизован вход: где входные наборы, где параметры, где owner, как привязывать к контракту данных.

Нет связки с релизным процессом. Проверки не «блокируют» промоут, не запускаются в smoke-режиме перед релизом.

Как сделать лучше (целевое решение)
1) Архитектура потока

Spec-driven (YAML) проверки → генерация SQL/джобов.

Единый “Registry” (справочник) + авто-инвентарь из YAML (валидация при CI/CD).

Единая краткая витрина dq_overview (ежезапуск), единая детальная витрина dq_detail (с JSON payload).

Run lifecycle: run_id, started_at, ended_at, status, rows_tested, rows_failed, data_version/partition_key.

Алертинг по порогам (thresholds из YAML) с умным подавлением (запуск в окне загрузки, авто-снижение шума).

Дашборд: обзор (SLA качества, топ-ошибки), с drill-down до деталей.

2) Схемы и размещение

Схема dq (или ops_dq) для логов (не dm).

Детали (много строк) — лучше в ClickHouse (быстро, дешево, партиции по дате/error_code). В GP хранить краткую.

Хранение: dq_overview — 180 дней, dq_detail — 30 дней (с ежедневной очисткой по партициям).

3) Модель данных (минимально, но достаточно)
dq.registry (справочник)

check_id (pk, например dq_sd_0001)

name, description, category (technical|business|freshness|…)

owner_team, owner_person, severity (P1–P4)

dataset, schema_name, table_name, partition_key

threshold_type (abs|pct), threshold_value

schedule (cron/rrule), enabled

source_yaml_path, created_at, updated_at

dq.overview (краткая)

run_id, check_id, run_started_at, run_ended_at, status (pass|warn|fail|error)

dataset, schema_name, table_name, data_version / partition_key

метрики: rows_tested, rows_failed, fail_pct, coverage_pct, freshness_sec

severity, message, link_to_detail, executor (DAG/task_id)

партиция по run_date (день)

dq.detail (единая детальная)

run_id, check_id, row_key (строковый ключ или hash), error_code, error_msg

dataset, schema_name, table_name, partition_key

payload_json (гибкая структура: конфликтующие поля, значения, diffs)

партиции: по дате / check_id (в CH — PARTITION BY toDate(run_started_at) ORDER BY (check_id,row_key))

Почему одна детальная таблица лучше: проще права, квоты, индексация, алерты, SQL; нет каскада DDL на каждую новую проверку; гибкий payload_json покрывает разнородные структуры.

4) Формат спецификации проверки (YAML)
check_id: dq_sd_0001
name: Uniqueness of sales order lines
category: technical
severity: P2
dataset: sales
schema: dds
table: sales_order_line
key_columns: [order_id, line_id]
logic:
  type: uniqueness
  sql: |
    SELECT order_id, line_id, COUNT(*) AS cnt
    FROM dds.sales_order_line
    WHERE load_dt = {{ ds }}
    GROUP BY 1,2
    HAVING COUNT(*) > 1
threshold:
  type: abs
  fail_if_rows_failed_gt: 0
retention:
  overview_days: 180
  detail_days: 30
alerting:
  notify: ["data-quality@company.com"]
  create_ticket: true
  jira_project: "DQ"


Для «бизнесовых» проверок logic.type: custom и даём SQL, который возвращает ровно строки-нарушители с ключом и описанием.

5) Исполнение (Airflow)

DAG per domain (финансы/сбыт/…); task per check (идемпотентные).

Оператор:

прогоняет SQL «нарушителей»,

пишет dq.detail с run_id,

пишет агрегат в dq.overview (rows_tested/failed/… и статус с учётом threshold),

если status in (fail,error) — шлёт алерт/создаёт тикет.

Idempotency: run_id = ${dag_id}_${ds}_${check_id}; перед записью делаем DELETE WHERE run_id=….

Порядок: зависимости тестов от таблиц: авто-построение по YAML (как вы уже делаете для витрин).

6) Алёртинг (чёткая политика)

Severity: P1 (блокирующие отчёты/клиентов), P2 (критичное отклонение), P3 (заметно), P4 (минор).

Порог: abs/pct; можно поддержать динамический порог (медиана ±10% за 7 дней) для шумных проверок.

Почта/Slack/Teams + автосоздание тикетов по P1–P2.

Suppression windows: не алертить в «окно ночных догрузок».

Escalation: если P1 не закрыт X часов — эскалация владельцу домена.

7) Категоризация и метрики качества

Категории (Completeness, Uniqueness, Validity, Consistency, Freshness, Integrity).

SLI/SLO: % проверок «зелёные», средний freshness_sec, среднее fail_pct, MTTR по DQ инцидентам.

Дашборд:

Главная: «здоровье доменов», тепловая карта проверок (по severity и статусу).

Drill-down: чек → динамика за 30/180 дней, топ-ключи нарушений, ссылка в CH на dq.detail.

Мини-DDL (пример на GP/CH)
Greenplum (краткая и справочник)
-- registry
CREATE TABLE dq.registry (
  check_id text PRIMARY KEY,
  name text, description text, category text, severity text,
  owner_team text, owner_person text,
  dataset text, schema_name text, table_name text, partition_key text,
  threshold_type text, threshold_value numeric,
  schedule text, enabled boolean,
  source_yaml_path text,
  created_at timestamp default now(), updated_at timestamp default now()
) DISTRIBUTED REPLICATED;

-- overview (партиция по дню)
CREATE TABLE dq.overview (
  run_date date,
  run_id text,
  check_id text,
  run_started_at timestamp,
  run_ended_at timestamp,
  status text,
  dataset text, schema_name text, table_name text,
  partition_key text, data_version text,
  rows_tested bigint, rows_failed bigint,
  fail_pct numeric, coverage_pct numeric,
  freshness_sec bigint,
  severity text,
  message text,
  link_to_detail text,
  executor text
) DISTRIBUTED BY (run_date);

ClickHouse (детали)
CREATE TABLE dq.detail
(
  run_started_at DateTime,
  run_id String,
  check_id String,
  dataset String, schema_name String, table_name String,
  partition_key String,
  error_code String,
  error_msg String,
  row_key String,
  payload_json JSON
)
ENGINE = MergeTree
PARTITION BY toDate(run_started_at)
ORDER BY (check_id, row_key);

Почему так лучше

Одна детальная таблица вместо N → проще эксплуатация, права, запросы, индексация, ретеншн.

Spec-driven → меньше ручных несоответствий, автогенерация задач, прозрачность.

Идемпотентность и run-модель → корректные перерасчёты, воспроизводимость, связь с релизом.

Пороговая логика и алёртинг → не просто «дашборд», а управляемый процесс с реакцией.

Метрики и категории → можно ставить цели по качеству (SLO) и показывать прогресс руководству.

Производительность → детали в ClickHouse, агрегаты в GP, партиции/TTL удаляют старь автоматически.
